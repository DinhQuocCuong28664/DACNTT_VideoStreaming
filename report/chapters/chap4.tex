\chapter{System Design}
\label{chap:design}

This chapter describes the architecture of the system, the transcoding pipeline, the database, the
protection of private content, the moderation of uploads, the interface and the API.

\section{High-Level Architecture}
\label{sec:architecture}

The system is organised into four tiers, shown in Figure~\ref{fig:architecture}: a client tier
running in the browser, a delivery tier built on Amazon CloudFront, an application tier
comprising the backend API and the database, and a processing tier that performs transcoding.

The separation between the application tier and the processing tier is the defining
characteristic of this design. The backend API never touches video content: it issues
pre-signed URLs, records metadata, and answers queries, while every byte of video flows
directly between the browser, Amazon S3, and CloudFront. This separation has three consequences
that together justify the architecture. The API server's resource consumption becomes
independent of video size and upload concurrency. The processing tier can scale according to
transcoding demand without affecting the responsiveness of the interface. And a failure in the
processing tier degrades the system gracefully, leaving already-published videos playable while
newly uploaded ones remain in a pending state.

Two later additions sit inside this structure and do not change it. Content moderation runs in the
processing tier, as the last step before a video is published, so that the check neither delays
the upload nor adds a component to operate (Section~\ref{sec:moderation-design}). And the console
that human reviewers use is a role-restricted part of the same single page application and the same
backend API, not a separate system.

Two design decisions in this sequence need explanation. The first is the order of record creation
and URL issuance. The backend creates the database record \emph{before} it generates the pre-signed
URL, and derives the S3 object key from the record's identifier. Generating the key first would
create a race: the S3 event could start transcoding before the record exists, and the job would
have no row to update. Creating the record first removes this failure entirely.

The second is protection against processing a video twice. The transcoder has two modes. In
\texttt{worker} mode, used during development, the container reads the SQS queue itself and, while
FFmpeg runs, keeps extending the visibility timeout of its message, a heartbeat, so that SQS does
not hand the same message to another consumer; the message is deleted only after success. The
deployed system runs \texttt{batch} mode: the Lambda submitter reads the message, submits an AWS
Batch job and deletes the message at once, and the container receives the video identifier as an
environment variable. On the deployed path there is therefore no heartbeat. Protection against a
duplicate rests on conditional database writes, which is where it belongs in any case, since a
renewal timer alone cannot guarantee mutual exclusion (Section~\ref{sec:transcoder-impl}), and
retry is provided by AWS Batch (Section~\ref{sec:challenges}). Worker mode is kept because it lets
the transcoder run against the queue without provisioning Batch.

\subsection{Upload of Large Files}
\label{sec:upload-design}

The sequence of Figure~\ref{fig:sequence} uses one pre-signed request, which suits files up to a
few hundred megabytes. For larger files the design switches to a multipart upload, because a single
transfer that fails near its end must be repeated in full and Amazon S3 accepts at most 5~GiB in one
request. The backend chooses the path from the declared size: a file of up to 512~MiB is sent with
one pre-signed POST, and a larger file is divided into parts of 32~MiB.

Both paths keep the payload away from the application server, and both let the storage service,
not the client, enforce the limits. For the single request, the signed policy fixes the object key,
the content type and the size range. For a multipart upload the backend signs one URL per part for
exactly that part's length, so S3 itself refuses a part of any other size, and when the client
reports completion the backend lists the parts that S3 holds before asking S3 to assemble the object.
The ceiling on file size is a configuration value with a hard limit of 20~GiB, which is 640 parts of
32~MiB, and the deployed system uses that limit. An abandoned upload is cleaned up twice over: a
lifecycle rule aborts incomplete multipart uploads after two days, and a periodic reconciler removes
a draft that has stayed in the \texttt{UPLOADING} state for more than a day.

\subsection{Chunk-Parallel Transcoding of Long Videos}
\label{sec:chunked-design}

The pipeline of Figure~\ref{fig:sequence} gives each video to one container. That suits short videos
and fails for long ones: on a single vCPU, FFmpeg ran four to five times slower than real time
(Sections~\ref{sec:pipeline-evaluation} and \ref{sec:chunked-evaluation}), so a long source would
exceed the two-hour limit of a job however many vCPUs the account holds. The design therefore divides
a video of five minutes or more into chunks that are encoded concurrently, and keeps the
single-container path for shorter videos, where splitting costs more than it saves.

The job that the Lambda submitter starts becomes a planner. It reads the structure of the source over
HTTP without downloading it and divides the video at boundaries that are whole multiples of a
six-second group of pictures, counted in frames so that a rate such as 29.97 frames per second does
not accumulate a fractional error. It then submits the jobs of Table~\ref{tab:chunked-jobs} to the
same AWS Batch service.

Three properties of this design are deliberate. The chunk array goes to a second, lower-priority
job queue that shares the Fargate Spot environment, so a short video submitted while a long one is
encoding runs ahead of the remaining chunks. The number of chunks follows the number of tasks that
can run at once, about three chunks per slot and none shorter than about a minute, so a larger quota
produces smaller chunks. And the planner does not split a source that cannot be split safely, meaning
a variable frame rate, an unknown duration, or audio and video that differ by more than 0.25~seconds;
such a video falls back to the single-container path and is not failed.

While a chunked video is encoding, its child jobs periodically touch the \texttt{updatedAt} field of
the video, because the reconciler that resets a video stuck in \texttt{PROCESSING} for more than six
hours would otherwise mistake a long, healthy encode for a stuck one. How this path performs is
measured in Section~\ref{sec:chunked-evaluation}.

The pipeline executes through five distinct stages:
\begin{enumerate}
\item \textbf{Stream Inspection and Probing:} The worker executes \texttt{ffprobe} to extract video
dimensions, frame rate, duration, and audio track layouts. If the source resolution is lower than
1080p, the ladder is automatically bounded at the source's native resolution, preventing
wasteful upscaling.
\item \textbf{Single-Decode Multi-Scale Filtergraph:} The video stream is decoded exactly once.
The uncompressed raw frames are piped through a multi-branch filtergraph that scales frames into
the six standard resolution tiers (1080p down to 144p).
\item \textbf{Strict Keyframe (GOP) Synchronization:} In ABR streaming, seamless bitrate switching
requires all renditions to place instantaneous decoder refresh (IDR) keyframes at the exact same
frame timestamps. FFmpeg is configured with \texttt{-g (fps*6) -keyint\_min (fps*6) -sc\_threshold 0},
enforcing identical six-second segment boundaries across all ladder rungs.
\item \textbf{AES-128 Envelope Encryption:} For copyright protection, the container generates a
cryptographically secure 16-byte symmetric key via \texttt{crypto.randomBytes(16)} and configures
FFmpeg's \texttt{-hls\_key\_info\_file}. Every \texttt{.ts} segment is encrypted with AES-128 CBC.
The key delivery URI embedded in the variant playlists directs client players to the authorized
endpoint (\texttt{/api/videos/:id/key}).
\item \textbf{Hierarchical Playlist Assembly:} The HLS muxer generates variant playlists indexing
the 6-second segments with precise \texttt{\#EXTINF:6.000000} duration tags. Finally, a master playlist
(\texttt{master.m3u8}) is written, carrying the \texttt{\#EXT-X-STREAM-INF} descriptors declaring
the resolution, codecs, and bandwidth ceilings of each rendition.
\end{enumerate}

The \texttt{Video} document carries a \texttt{status} field that acts as a state machine with four

failed to transcode is distinguishable from one that is merely slow.

Likes and dislikes are stored as arrays of user identifiers inside the video document rather than
as a separate collection, because the counts are always read with the video and a user can appear at
most once in each array. This holds at the scale of the project only. On a widely viewed video the
arrays grow towards MongoDB's document size limit, and a listing of twelve videos reads every
identifier in all twenty-four arrays merely to show counts. The usual remedy, a separate collection
with a compound unique index on video and user plus a counter on the video, is the right structure
for popular content; it was not adopted because of scale, not because the embedded form is better.

Search matches a case-insensitive regular expression against the title, description and tags. No
index can serve an unanchored regular expression, so every search scans the collection, which is
acceptable at this scale. A text index would be faster but would change the behaviour, since it
matches neither parts of words nor the tags; an unused text index that the schema once declared was
therefore removed.

\section{Content Protection Design}
\label{sec:content-protection}

Protecting private content requires two mechanisms, because each addresses a different threat.

Origin Access Control makes the processed S3 bucket private and grants read access only to the
CloudFront distribution through a bucket policy. A viewer therefore cannot bypass the content
delivery network and fetch objects from S3 directly, which would both escape any access control at
the edge and incur higher transfer charges.

Origin Access Control alone does not decide \emph{who} may retrieve content through CloudFront.
Without a second mechanism, anyone holding a manifest URL could download a video whatever its
visibility, which would make the private mode ineffective. The system therefore adds CloudFront
Signed Cookies backed by a trusted key group \cite{awscloudfrontprivate}. The backend checks the
requester's permission with the same service function that governs the API response, signs a policy
scoped to the directory of that one video, and sets the cookies on the response; CloudFront refuses
any request without a valid signature with HTTP 403 at the edge. Figure~\ref{fig:playback-sequence}
shows the exchange.

\begin{figure}[H]
\centering
\includegraphics[width=\textwidth]{images/17-playback-sequence.png}
\caption{\textit{Sequence diagram of playback authorisation: the backend issues Signed Cookies for
one video, and CloudFront checks them on every request}}
\label{fig:playback-sequence}
\end{figure}

Signed cookies were chosen over signed URLs because of the structure of HLS. A playback session
fetches a manifest and then hundreds of segments, each as a separate request. Signing each URL would
require rewriting every entry of the manifest, typically in an edge function, which adds complexity
and cost, whereas one set of cookies covers the whole directory and the browser attaches it to every
request. The policy is a custom policy rather than a canned one, because a canned policy does not
allow a wildcard in the resource path, and the required scope is the directory of one video: its
manifest and all its segments, and nothing more.

The edge does not distinguish one visibility level from another. Every manifest and segment requires
a valid signature, and visibility decides only whether the backend issues the cookies at all. A
cookie covers one video, while a catalogue page shows the thumbnails of many, so the thumbnail path
has its own cache behaviour that needs no signature. A thumbnail is a single low-resolution still
already shown in listings; the protected unit is the stream, not every byte that belongs to a video.

\section{Content Moderation and Operations Design}
\label{sec:moderation-design}

A platform that publishes what its users upload has to decide, for each upload, whether it may be
shown. No single check can be trusted with that decision, because an automatic classifier errs in
both directions: it removes harmless videos, which are false positives, and it lets harmful ones
through, which are false negatives. The design therefore stacks four layers, each of which can
correct the one before it: automatic screening, reports from viewers, review by staff, and a random
audit of what was approved. It also records every human decision together with what the machine had
concluded, so that the error rates of the earlier layers can be estimated and not assumed.
Figure~\ref{fig:moderation-sequence} follows one video through screening, a report, a decision and an
appeal; the subsections below explain each step.

\centering

\subsection{Automatic Screening}
\label{sec:screening-design}

Screening runs inside the job that finishes the video and writes its verdict in the same
conditional write that marks the video \texttt{READY}, so a video is never published without a
verdict unless screening was switched off explicitly. On the single-container path it runs before
transcoding, and on the chunked path in the finalizer. A video that is blocked is still transcoded,
so that staff can watch it when its owner appeals.

The job samples one frame every five seconds, at most 120 frames, scaled to at most 720 pixels
wide, and sends each to the image moderation operation of Amazon Rekognition
\cite{awsrekognitionmoderation}. The image operation was preferred to the video operation for a
concrete reason: the video operation accepts stored videos only if they are encoded with H.264 in
an MPEG-4 or MOV container and are at most 10~GB \cite{awsrekognitionlimits}, whereas the platform
accepts MKV, WebM and AVI uploads of up to 20~GiB, and FFmpeg in the container can decode all of
them. The image operation also runs synchronously inside a job that is already running, so it needs
no notification topic and no polling, and its cost has a ceiling: at the Singapore list price of
0.00125~USD per image, for the first million images of the month, a video costs at most 0.15~USD.
The price of this choice is that sparse sampling can miss content that appears for less than the
interval between two samples, which is why screening is the first layer and not the only one.

Each label returned for a frame is looked up in a policy table that maps it to one of three actions
(Table~\ref{tab:label-policy}). The table sets policy at the coarse levels of the label taxonomy
and uses the finest level only to exclude a specific concept, so that a bare male chest, for
example, does not send a video to review merely because its parent label is non-explicit nudity.

Two refinements keep the policy from over-reaching. A frame that Rekognition classifies as
animated or illustrated with at least 80\% confidence lowers graphic violence and death from
\emph{block} to \emph{review}, since violence in a game or a cartoon is not the violence the rule is
about; explicit sexual content and hate symbols are not lowered, because a drawing violates the
rule as much as a photograph does. And screening fails closed: a video for which no frame could be
analysed, or fewer than 80\% of the planned frames, is held back for review and is not published,
so that an unavailable service produces a delay and not a publication.

\subsection{Moderation States and Visibility}

The verdict is stored as \texttt{approved}, \texttt{flagged} or \texttt{blocked}, independently of
the transcoding status of Section~\ref{sec:database-design}: a video can be \texttt{READY} and still
hidden. A flagged video appears in no listing and is visible only to its owner and to staff. A
blocked video can be played by staff alone, and its owner can appeal the removal. The filter that
implements this is one function used by every public query path, for the reason given for
authorisation in Section~\ref{sec:backend-impl}: copies of a rule drift apart. A video uploaded
before moderation existed carries no verdict and is treated as approved.

\subsection{Review, Appeals and Audit}
\label{sec:review-design}

Amazon's own guidance expects people to review a small share of the content, typically one to five
per cent of the total volume, already flagged by the model \cite{awsrekognitionmoderation}. Staff
clear the review queue by approving or blocking each video, and every decision must carry a reason
code from a short, closed list: for an approval, for example, a model error, fiction or a game, or
an acceptable context; for a removal, for example content missed by the model, an upheld report or
a failed audit; and, for a video that the machine has already removed, a confirmation that it was
right. The list is closed because free text cannot be counted, whereas a count of how many
removals were reversed because the content was a game points to the threshold that needs adjusting.

Each decision is appended to an event log that records who decided and in which role, the verdict
before and after, the conclusion the machine had reached, the reason code, and the outcome class of
Table~\ref{tab:outcome-classes}. The machine's conclusion is copied onto the video once, immediately
before a person first changes the verdict; without that snapshot the first human decision would
overwrite the very fact needed to say whether the machine was right. No route edits or deletes an
event, because the auditor's work depends on the log being intact.

The owner of a removed video can appeal, once per decision, with a message of at most 500
characters; a new decision, such as the video being restored and later removed again, allows a new
appeal. A person who does not own the video receives a not-found response, for the same reason as
for visibility, and an operator resolves the appeal as upheld or rejected with a note. This follows
the Santa Clara Principles, which ask a platform to notify the person affected and to offer an
appeal that is reviewed by a person who took no part in the first decision
\cite{santaclara2021}. Appeals are also the most reliable source of false positives, since only
the owner has a reason to say that the machine was wrong.

False negatives are harder to find, because a missed video is one among thousands that were approved
and viewer reports see only the most conspicuous of them. The design therefore draws a random sample
of approved videos, which staff label \emph{pass} or \emph{fail}; the proportion of failures in the
sample estimates the rate at which violating videos get through. A video can enter a sample only
once, so its label is never counted twice.

\subsection{Measuring the Screening}

The console reports four figures, each with its denominator and a 95\% Wilson confidence interval
\cite{wilson1927}: the share of automatic removals that staff reversed, which is the false positive
rate; the share of flags that staff confirmed, which is the precision of the flag; the share of each
group that has been reviewed at all, which is coverage; and the false negative rate. The Wilson
interval suits small counts, because unlike the normal approximation it stays between zero and one
and remains usable when the observed rate is near zero. The false negative rate comes only from the
random audit and never from viewer reports, which would bias it low, and a video that no one has
reviewed enters no rate. Confirming a removal that the machine made is a separate action, because
such a video goes straight to the Removed list, where the only other action is to restore it.
Without the confirmation, the reviewed removals would be only those that staff reversed and the
false positive rate would be computed over reversals alone; with it, a confirmed removal is a true
positive and stays in the denominator.

\subsection{Verifying the Owner of an Account}
\label{sec:verification-design}

Registration checks only that an e-mail address is well formed, so anyone can register with an
address that belongs to someone else. Two harms follow. The registrant can upload, the most expensive
operation of the system, under another person's address, which makes uploads anonymous in practice.
And when the real owner later signs in with Google, the account is already held by someone who knows
its password. The design therefore asks each new account to prove that it receives mail at its
address, and lets only verified accounts upload. Figure~\ref{fig:verification-sequence} shows both
ways of proving it.

\begin{figure}[H]
\centering
\includegraphics[width=\textwidth]{images/18-verification-sequence.png}
\caption{\textit{Sequence diagram of account verification: following the e-mailed link, or signing
in with Google at the same address}}
\label{fig:verification-sequence}
\end{figure}

After registration the backend generates a random token of 32 bytes, stores only its SHA-256 hash with
an expiry of 24 hours, and e-mails a link that carries the token itself, as it does for a password
reset. The link opens a page of the single page application, and that page sends the token in a POST
request, so a mail client that previews links by fetching them cannot verify the account by itself.
The server consumes the token in one conditional update, so two clicks on the same link cannot both
succeed. An unverified account can still browse, like and comment, but the upload endpoint refuses it
with a distinct error code, which the interface turns into a reminder with a button that sends the
link again, limited to five mails per hour for each account and, whoever asks, to five per hour for
each recipient address.

Three events count as proof of ownership: following the link; signing in with Google, whose identity
token carries an address that Google has verified; and completing a password reset, since the reset
link also goes only to the mailbox. A Google sign-in whose address matches an unverified local account
takes that account over: the password is removed, every token issued earlier is invalidated through
the password-change timestamp, and any pending verification or reset token is deleted, so whoever
registered first cannot keep access. A verified account is never merged automatically; its owner must
sign in with the password and link Google from the settings page.

\section{Interface Design}
\label{sec:interface-design}

Figure~\ref{fig:user-flow} sets out the paths a user can take through the application. Two of its
properties constrain the design.

The first is that the catalogue and the watch page are reachable without an account. Browsing,
searching, filtering by category and playing a public video all work for an anonymous visitor, and
authentication is demanded only where an action requires an identity: uploading, commenting,
reacting, or managing one's own channel. A visitor who reaches the upload page without a session is
diverted through sign-in or registration and returned to it, rather than asked to sign in on arrival.

The second is that the upload path does not end where the user's involvement ends. Once the browser
has sent the file to Amazon S3, the interface returns control at once and the video enters the
\texttt{PROCESSING} state, in which only its owner sees it, on the channel management view. Only when
the pipeline marks it \texttt{READY} does it join the catalogue. The interface therefore has to show
a video that exists but cannot yet be played, which is why the state machine of
Section~\ref{sec:database-design} is explicit. The same holds after the pipeline: a video that
screening held back is visible to its owner and not in the catalogue until a person approves it.

\begin{figure}[htbp]
\centering
\includegraphics[width=\textwidth]{images/08-user-flow.png}
\caption{\textit{User flow through the application, from an anonymous visit to a published video}}
\label{fig:user-flow}

The frontend is a single page application of functional React components with hooks, using React
Context for authentication and theme state. Redux was unnecessary at this scale, since the shared
state is only the current user and the selected theme.

The interface is available in Vietnamese and English, chosen by a control in the header and
remembered in the browser. Adding a second language constrained the data model as well as the
presentation. Video categories are stored as Vietnamese strings, and the schema validates each new
video against exactly those strings, so translating a category would have made the catalogue filter
and the upload form reject valid input. The display label and the stored value are therefore kept
apart: the client shows a translated label but always sends the original value. Messages from the API
are likewise chosen from the request's \texttt{Accept-Language} header.

The video player is a custom component rather than the browser's native controls, because native
controls cannot be extended: the browser has its own menu for playback speed and picture-in-picture,
which cannot be merged with the quality selector of HLS.js. To avoid two unrelated menus, the
component reimplements play and pause, seeking, volume, fullscreen, playback speed,
picture-in-picture and rendition selection within one settings menu.

The player also decides when a view is counted. Instead of incrementing the counter when the page
loads, which repeated refreshes could inflate, the component adds up the time actually played,
leaving out seeks, and notifies the page after thirty seconds, or at the end of a video shorter
than that; the server also ignores repeated reports from the same viewer within thirty minutes
and never counts the owner's own views.

The operations console is part of the same application, at its own address and reachable only by
staff. Its tabs are the review queue, the removed videos, appeals, audit samples, the rates, the
event log and the users, and a person sees only the tabs that the permissions of their role allow, so
an operator never sees the rates and an auditor never sees a decision button. Thumbnails of videos
under review stay blurred until a reviewer reveals them, so that reading the queue does not by itself
expose staff to the content.

\section{Performance and Auto-Scaling Architecture}
\label{sec:scaling-architecture}

The platform's capability to withstand volatile user traffic without manual operational intervention
is governed by an event-driven, multi-tier elasticity model. The system decouples interactive web
traffic, computational video transcoding, and high-volume media delivery into independent scaling
domains, as outlined below.

\subsection{Event-Driven Serverless Compute Elasticity}

Unlike conventional monolithic architectures that provision long-running virtual machines or EC2
clusters for media processing, the transcoding tier operates entirely on AWS Batch with Fargate
(Spot and On-Demand) compute environments. This achieves true scale-to-zero elasticity:
\begin{itemize}
\item \textbf{Idle Phase (Zero Cost):} When no videos are pending in Amazon SQS, the Batch compute
environment provisions 0 vCPUs and 0 instances. Idle compute cost is mathematically zero.
\item \textbf{Burst Scaling Phase:} When multiple users upload videos simultaneously, Amazon S3
triggers event notifications into SQS. The Lambda job submitter consumes queue messages and
enqueues tasks into the AWS Batch Job Queue. AWS Batch evaluates the backlog and scales Fargate
tasks horizontally, provisioning isolated container instances for each job up to the account quota.
\item \textbf{Automatic Scale-Down:} Upon successful HLS generation and database synchronization,
the container process exits with code 0. AWS Batch detects container termination and releases the
Fargate infrastructure within minutes, eliminating idle compute expenses.
\end{itemize}

\subsection{Chunk-Parallel Speedup for Long-Duration Media}

For long-duration videos exceeding five minutes, the platform breaks the single-container
bottleneck via chunked horizontal parallelism (Section~\ref{sec:chunked-design}). Total transcoding
time scales inversely with the number of parallel chunk workers: $T(N) = T_{\mathrm{plan}} + \max_i(T_{\mathrm{chunk},i}) + T_{\mathrm{final}}$,
where $T_{\mathrm{plan}}$ represents initial metadata probing (around 3~seconds), $T_{\mathrm{chunk},i}$
is the encoding duration of chunk $i$, and $T_{\mathrm{final}}$ is playlist stitching (around 8~seconds).
Because chunks execute concurrently across independent Fargate Spot tasks, total processing time
decreases significantly, slashing transcoding latency by up to 65 percent on long sources (Section~\ref{sec:chunked-evaluation}).

\subsection{Edge Offloading and Delivery Scale}

The delivery tier delegates media distribution to Amazon CloudFront with Origin Access Control (OAC).
Because video segments are immutable once written, CloudFront caches HLS transport stream segments
(\texttt{.ts}) at edge locations with long time-to-live (TTL) headers. Edge cache hit ratios exceed
98 percent, effectively shielding the private S3 Processed bucket from request spikes and ensuring that
concurrent viewers experience low Time-to-First-Frame (TTFF) without saturating origin network interfaces.

\subsection{Application Layer Scaling and Future Evolution}

While the transcoding and delivery tiers scale elastically, the backend application API currently
operates on a single EC2 instance (\texttt{t3.small}) behind Cloudflare proxying. This design choice
minimized operational complexity during initial development but represents the primary single point
of failure (SPOF) and concurrency bottleneck of the platform.

To scale the application tier to enterprise workloads, the architectural evolution path comprises:
(1) migrating the Node.js API into an AWS ECS Fargate service spanning multiple Availability Zones
behind an Application Load Balancer (ALB); (2) introducing an Amazon ElastiCache (Redis) in-memory
caching layer to absorb view-counter deduplication, JWT blacklist validation, and hot video metadata
queries; and (3) replacing MongoDB collection scans with dedicated full-text search indexing to
prevent database CPU exhaustion under concurrent search queries.
