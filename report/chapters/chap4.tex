\section{High-Level Architecture}
\label{sec:architecture}

The system is organised into four tiers, shown in Figure~\ref{fig:architecture}: a client tier
running in the browser, a delivery tier built on Amazon CloudFront, an application tier
comprising the backend API and the database, and a processing tier that performs transcoding.

The separation between the application tier and the processing tier is the defining
characteristic of this design. The backend API never touches video content: it issues
pre-signed URLs, records metadata, and answers queries, while every byte of video flows
directly between the browser, Amazon S3, and CloudFront. This separation has three consequences
that together justify the architecture. The API server's resource consumption becomes
independent of video size and upload concurrency. The processing tier can scale according to
transcoding demand without affecting the responsiveness of the interface. And a failure in the
processing tier degrades the system gracefully, leaving already-published videos playable while
newly uploaded ones remain in a pending state.

Two later additions sit inside this structure and do not change it. Content moderation runs in the
processing tier, as the last step before a video is published, so that the check neither delays
the upload nor adds a component to operate (Section~\ref{sec:moderation-design}). And the console
that human reviewers use is a role-restricted part of the same single page application and the same
backend API, not a separate system.

Two design decisions embedded in this sequence merit explanation.

The first concerns the ordering of database record creation and URL issuance. The backend
creates the database record \emph{before} generating the pre-signed URL, and derives the S3
object key from the identifier of that record. The alternative, generating a key first and
creating the record afterwards, introduces a race condition: the S3 event notification can
arrive and trigger transcoding before the record exists, at which point the transcoder has no
row to update and the job fails. Creating the record first eliminates this class of failure
entirely.

The second concerns the visibility timeout of the SQS message. Amazon SQS hides a message from
other consumers for a configured period after it is received, and redelivers it if the consumer
has not deleted it by then. Transcoding a large file can easily exceed any reasonable fixed
timeout, which would cause the same video to be processed twice concurrently. The transcoder
therefore implements the heartbeat pattern: while FFmpeg runs, a timer periodically extends the
visibility timeout of the in-flight message. The message is deleted only after the job
completes successfully. If the container crashes, the heartbeat stops, the timeout lapses, and
the message returns to the queue for another attempt.

That description is accurate about the transcoder's \texttt{worker} mode, in which the container
consumes from the queue itself, but it is important to be precise that this is not the mode the
deployed system runs. The container image and the AWS Batch job definition both invoke
\texttt{batch} mode, in which the video identifier and object key arrive as environment variables
and the container never contacts SQS at all. The queue is consumed instead by the Lambda
submitter, which reads the message, submits a Batch job, and returns immediately. Because the
Lambda's work is finished at that point, the message is deleted when the job is \emph{submitted},
not when transcoding completes.

The consequence is that on the deployed path there is no heartbeat, and the message is long gone
before FFmpeg starts. Two properties the pattern was chosen to provide therefore have to be
obtained elsewhere. Protection against duplicate processing rests entirely on the conditional
database writes described in Section~\ref{sec:transcoder-impl}, which is where it belongs in any
case, since Burrows' analysis of leases (Section~\ref{sec:testing}) shows that a renewal timer
cannot by itself guarantee mutual exclusion. Retrying a failed job, which the heartbeat design
delegated to SQS redelivery, has no equivalent unless AWS Batch is configured to provide it; that
it originally was not is discussed in Section~\ref{sec:challenges}.

Retaining the worker-mode implementation is a deliberate choice rather than an oversight: it
allows the transcoder to be run against the queue directly during development without provisioning
Batch. Recording which of the two modes the evaluated system actually executes matters, though,
because a mechanism present in the source but absent from the deployed path cannot be credited
with the guarantees it would provide if it ran. Section~\ref{sec:challenges} draws the same
distinction about content protection.

\subsection{Upload of Large Files}
\label{sec:upload-design}

The sequence of Figure~\ref{fig:sequence} uses one pre-signed request, which suits files up to a
few hundred megabytes. For larger files the design switches to a multipart upload, because a single
transfer that fails near its end must be repeated in full and Amazon S3 accepts at most 5~GiB in one
request. The backend chooses the path from the declared size: a file of up to 512~MiB is sent with
one pre-signed POST, and a larger file is divided into parts of 32~MiB.

Both paths keep the property that motivated direct upload, that the payload never passes through
the application server, and both keep the limits enforced by the storage service and not by the
client. For the single request, the signed policy fixes the object key, the content type and the
size range. For a multipart upload the backend signs one URL per part for exactly that part's
length, so S3 itself refuses a part of any other size, and when the client reports the upload
complete the backend lists the parts that S3 holds and checks them before it asks S3 to assemble
the object. The ceiling on the size of a file is a configuration value, with a hard limit of
20~GiB in the source, which is 640 parts of 32~MiB, and 20~GiB in the deployed system. An upload that
is abandoned is cleaned up in two ways: a lifecycle rule aborts incomplete multipart uploads after
two days, and a periodic reconciler in the backend removes a draft that has stayed in the
\texttt{UPLOADING} state for more than a day.

\subsection{Chunk-Parallel Transcoding of Long Videos}
\label{sec:chunked-design}

The pipeline of Figure~\ref{fig:sequence} gives each video to one container. That is adequate for
short videos and fails for long ones: on a single vCPU, FFmpeg ran roughly four to five times
slower than real time in the measurements of Sections~\ref{sec:pipeline-evaluation} and
\ref{sec:chunked-evaluation}, so a long source
would exceed the two-hour limit placed on a job however many vCPUs the account holds. The design
therefore divides a video of five minutes or more into chunks that are encoded concurrently, and
keeps the single-container path for shorter videos, where splitting costs more than it saves.

The job that the Lambda submitter starts becomes a planner. It reads the structure of the source
over HTTP without downloading it and divides the video at boundaries that are whole multiples of a
six-second group of pictures, counted in frames so that a rate such as 29.97 frames per second does
not accumulate a fractional error. It then submits the jobs of Table~\ref{tab:chunked-jobs} to the
same AWS Batch service.

Three properties of this design are deliberate. The chunk array goes to a second, lower-priority
job queue that shares the Fargate Spot environment of the main queue, so that a short video
submitted while a long one is encoding is scheduled ahead of its remaining chunks and does not wait
for all of them. The number of chunks follows the number of tasks that can run at once, about three
chunks per slot and none shorter than about a minute, so a larger quota produces smaller chunks.
And the planner declines to split a source that cannot be split safely, which means a variable frame
rate, an unknown duration, or audio and video that differ by more than 0.25~seconds; such a video
falls back to the single-container path and is not failed.

While a chunked video is encoding, its child jobs periodically touch the \texttt{updatedAt} field
of the video. The reconciler that returns a video stuck in \texttt{PROCESSING} for more than six
hours to a consistent state would otherwise mistake a long and healthy encode for a stuck one. How
this path behaves, including where adding vCPUs stops helping, is measured in
Section~\ref{sec:chunked-evaluation}.

Likes and dislikes are stored as arrays of user identifiers embedded within the video document
rather than as a separate collection. The denormalisation is justified at this scale because the
counts are always read together with the video, and because a single user can appear at most once
in each array, so the arrays cannot grow through repeated interaction by the same person.

It should not be justified more strongly than that. Uniqueness bounds each array by the number of
distinct users, which is a bound only in the formal sense; on a widely viewed video it is exactly
the growth that a document store is poorly suited to hold, against MongoDB's document size limit.
The cost is also paid on reads that do not want it, since a listing of twelve videos retrieves
every identifier in all twenty-four arrays merely to display counts. The conventional remedy is a
separate collection with a compound unique index on video and user, plus a denormalised counter on
the video. That is the right structure for a system expecting popular content, and the reason it
was not adopted here is scale rather than principle. That is a different claim from the design
being correct in general, and it is recorded as such.

Indexes are defined to match the actual query patterns. A compound index on visibility, status,
and creation time supports the home page listing, which always filters on the first two fields
and sorts on the third.

Search is the exception. The collection carried a text index on title and description, described as supporting
the search feature, but no query ever used it: search is implemented as a case-insensitive regular
expression matched against title, description and tags, and MongoDB cannot serve an unanchored
regular expression from an index. Every search was a full collection scan, and the index cost
write throughput and storage while serving nothing. The index has been removed rather than the
query rewritten, because switching to a text search would change the feature's behaviour and not
merely its cost: the regular expression matches substrings inside words and covers the tags field,
neither of which a text index does. At the scale of this project a full scan is acceptable.

\section{Content Protection Design}
\label{sec:content-protection}

Protecting private content requires two complementary mechanisms, because each addresses a
different threat.

Origin Access Control makes the processed S3 bucket entirely private and grants read access
exclusively to the CloudFront distribution through a bucket policy. This prevents a viewer from
bypassing the content delivery network and fetching objects directly from S3, which would both
circumvent any access control implemented at the edge and incur higher data transfer charges.

Origin Access Control alone, however, does not determine \emph{who} may retrieve content
through CloudFront. Without a second mechanism, any person holding a manifest URL can download
the video regardless of its visibility setting, which would make the private mode ineffective
in practice. The system therefore adds CloudFront Signed Cookies backed by a trusted key group
\cite{awscloudfrontprivate}. The backend verifies the requester's permission using exactly the
same service function that governs the API response, signs a policy scoped to the directory of
that single video, and sets the resulting cookies on the response. CloudFront rejects any
request lacking a valid signature with HTTP 403 at the edge.

Signed cookies were chosen over signed URLs because of the structure of HLS. A playback session
retrieves a manifest and then hundreds of individual segment files, each as a separate request.
Signing each URL individually would require rewriting every entry inside the manifest,
typically using an edge function, which adds considerable complexity and cost. A single set of
cookies covers the entire directory and is attached automatically by the browser to every
subsequent request.

The policy is signed as a custom policy rather than a canned policy. This distinction is not
cosmetic: a canned policy does not permit wildcards in the resource path, whereas the required
scope is an entire directory. The custom policy expresses the resource as a pattern covering
the manifest and all segments of one specific video, which grants exactly the access needed and
no more.

One consequence of this design deserves stating precisely, because it is easy to describe the
scheme as protecting private videos and thereby understate it. The edge does not distinguish
one visibility level from another: \emph{every} manifest and segment requires a valid signature,
and a request without one is refused whatever the video's visibility. What visibility governs is
the authorisation decision made earlier, when the backend decides whether to issue cookies at
all. All three levels are thus protected identically at the edge and differ only in who can
obtain the credential.

That uniformity has a limit that the design has to accommodate. A cookie authorises exactly one
video's directory, whereas a catalogue page renders thumbnails for many videos at once, and no
single cookie can cover them. Rather than weaken the policy scope to span the whole bucket, the
distribution carves out a separate cache behaviour for the thumbnail path that requires no
signature. The justification is that a thumbnail is not the asset the mechanism exists to
protect: it is a single low-resolution still, already shown to anyone permitted to see the video
in a listing, and treating it as public costs nothing that the scheme was designed to prevent.
The narrower point is that the protected unit is the stream, not every byte associated with a
video.

\section{Content Moderation and Operations Design}
\label{sec:moderation-design}

A platform that publishes what its users upload has to decide, for each upload, whether it may be
shown. No single check can be trusted with that decision, because an automatic classifier errs in
both directions: it removes harmless videos, which are false positives, and it lets harmful ones
through, which are false negatives. The design therefore stacks four layers, each of which can
correct the one before it: automatic screening, reports from viewers, review by staff, and a random
audit of what was approved. It also records every human decision together with what the machine had
concluded, so that the error rates of the earlier layers can be estimated and not assumed.

\subsection{Automatic Screening}
\label{sec:screening-design}

Screening runs inside the job that finishes the video and writes its verdict in the same
conditional write that marks the video \texttt{READY}, so a video is never published without a
verdict unless screening was switched off explicitly. On the single-container path it runs before
transcoding, and on the chunked path in the finalizer. A video that is blocked is still transcoded,
so that staff can watch it when its owner appeals.

The job samples one frame every five seconds, at most 120 frames, scaled to at most 720 pixels
wide, and sends each to the image moderation operation of Amazon Rekognition
\cite{awsrekognitionmoderation}. The image operation was preferred to the video operation for a
concrete reason: the video operation accepts stored videos only if they are encoded with H.264 in
an MPEG-4 or MOV container and are at most 10~GB \cite{awsrekognitionlimits}, whereas the platform
accepts MKV, WebM and AVI uploads of up to 20~GiB, and FFmpeg in the container can decode all of
them. The image operation also runs synchronously inside a job that is already running, so it needs
no notification topic and no polling, and its cost has a ceiling: at the Singapore list price of 0.00125~USD per
image, for the first million images of the month, a video costs at most 0.15~USD. The price of this choice is that sparse sampling can miss
content that appears for less than the interval between two samples, which is why screening is the
first layer and not the only one.

Each label returned for a frame is looked up in a policy table that maps it to one of three actions
(Table~\ref{tab:label-policy}). The table sets policy at the coarse levels of the label taxonomy
and uses the finest level only to exclude a specific concept, so that a bare male chest, for
example, does not send a video to review merely because its parent label is non-explicit nudity.

Two refinements keep the policy from over-reaching. A frame that Rekognition classifies as
animated or illustrated with at least 80\% confidence lowers graphic violence and death from
\emph{block} to \emph{review}, since violence in a game or a cartoon is not the violence the rule is
about; explicit sexual content and hate symbols are not lowered, because a drawing violates the
rule as much as a photograph does. And screening fails closed: a video for which no frame could be
analysed, or fewer than 80\% of the planned frames, is held back for review and is not published,
so that an unavailable service produces a delay and not a publication.

\subsection{Moderation States and Visibility}

The verdict is stored as \texttt{approved}, \texttt{flagged} or \texttt{blocked}, independently of
the transcoding status of Section~\ref{sec:database-design}. Whether a video has finished encoding
says nothing about whether it may be shown, and a video can be \texttt{READY} and still hidden. A
flagged video appears in no listing and is visible only to its owner and to staff. A blocked video
can be played by staff alone, and its owner can appeal the removal. The filter that implements this
is one function used by every public query path, for the reason given for authorisation in
Section~\ref{sec:backend-impl}: copies of a rule drift apart. A video uploaded before moderation
existed carries no verdict and is treated as approved.

\subsection{Review, Appeals and Audit}
\label{sec:review-design}

Amazon's own guidance expects people to review a small share of the content, typically one to five
per cent of the total volume, already flagged by the model \cite{awsrekognitionmoderation}. Staff
clear the review queue by approving or blocking each video, and every decision must carry a reason
code from a short, closed list: for an approval, for example, a model error, fiction or a game, or
an acceptable context; for a removal, for example content missed by the model, an upheld report or
a failed audit. The list is closed because free text cannot be counted, whereas a count of how many
removals were reversed because the content was a game points to the threshold that needs adjusting.

Each decision is appended to an event log that records who decided and in which role, the verdict
before and after, the conclusion the machine had reached, the reason code, and the outcome class of
Table~\ref{tab:outcome-classes}. The machine's conclusion is copied onto the video once, immediately
before a person first changes the verdict. Without that snapshot the first human decision would
overwrite the very fact that is needed to say whether the machine was right. No route edits or
deletes an event, because the auditor's work depends on the log being intact.

The owner of a removed video can appeal, once per decision, with a message of at most 500
characters; a new decision, such as the video being restored and later removed again, allows a new
appeal. A person who does not own the video receives a not-found response, for the same reason as
for visibility, and an operator resolves the appeal as upheld or rejected with a note. This follows
the Santa Clara Principles, which ask a platform to notify the person affected and to offer an
appeal that is reviewed by a person who took no part in the first decision
\cite{santaclara2021}. Appeals are also the most reliable source of false positives, since only
the owner has a reason to say that the machine was wrong.

False negatives are harder to find, because a missed video is one among thousands that were approved
and viewer reports see only the most conspicuous of them. The design therefore draws a random sample
of approved videos, which staff label \emph{pass} or \emph{fail}; the proportion of failures in the
sample estimates the rate at which violating videos get through. A video can enter a sample only
once, so its label is never counted twice.

\subsection{Measuring the Screening}

The console reports four figures, each with its denominator and a 95\% Wilson confidence interval
\cite{wilson1927}: the share of automatic removals that staff reversed, which is the false positive
rate; the share of flags that staff confirmed, which is the precision of the flag; the share of each
group that has been reviewed at all, which is coverage; and the false negative rate. The Wilson
interval is used because the counts are small, and unlike the normal approximation it stays within
zero and one and remains usable when the observed rate is near zero. The false negative rate comes
only from the random audit and never from viewer reports, which would bias it low. A video that no
one has reviewed is reported as unverified and enters no rate.

error rates is not the person whose decisions produce them, so the monitoring does not depend on the
monitored.

the auditor can read.

\subsection{Verifying the Owner of an Account}
\label{sec:verification-design}

Registration checks that an e-mail address is well formed and nothing more, so anyone can register
with an address that belongs to someone else. Two harms follow. The registrant can upload, the most
expensive operation of the system, under another person's address, which makes uploads anonymous in
practice. And when the real owner of the address later signs in with Google, the account is already
taken by someone who knows its password. The design therefore asks each new account to prove that it
can receive mail at its address, and lets only verified accounts upload.

After registration the backend generates a random token of 32 bytes, stores only its SHA-256 hash with
an expiry of 24 hours, and e-mails a link that carries the token itself, as is done for the tokens of
a password reset. The link opens a page of the single page application, and that page sends the token
in a POST request, so that a mail client that previews links by fetching them cannot verify the
account by itself. The server consumes the token in one conditional update, so two clicks on the same
link cannot both succeed. An account that has not verified its address can still browse, like and
comment, but the upload endpoint refuses it with a distinct error code, which the interface turns
into a reminder with a button that sends the link again, limited to five mails per hour for each
account and, whoever asks, to five per hour for each recipient address.

Three events count as proof of ownership: following the link; signing in with Google, whose identity
token carries an address that Google has verified; and completing a password reset, since the reset
link also goes only to the mailbox. A Google sign-in whose address matches an unverified local account
takes that account over. The password is removed, every token issued earlier is invalidated through
the password-change timestamp, and any pending verification or reset token is deleted, so that
whoever registered first cannot keep access. An account that is already verified is never merged
automatically: its owner must sign in with the password and link Google from the settings page.

\section{Interface Design}
\label{sec:interface-design}

Figure~\ref{fig:user-flow} sets out the paths a user can take through the application, and it is
worth reading before the component-level discussion that follows, because two of its properties
constrain the design.

The first is that the catalogue and the watch page are reachable without an account. Browsing,
searching, filtering by category and playing a public video all work for an anonymous visitor, and
authentication is demanded only at the point where an action requires an identity, which in
practice means uploading, commenting, reacting, or managing one's own channel. A visitor who
reaches the upload page without a session is therefore diverted through sign-in or registration
and returned to it, rather than being asked to sign in on arrival.

The second is that the upload path does not end where the user's involvement ends. Once the
browser has transferred the file directly to Amazon S3, the interface returns control immediately
and the video enters the \texttt{PROCESSING} state, in which it is visible only to its owner on
the channel management view. Only when the pipeline marks it \texttt{READY} does it join the
public catalogue. The interface consequently has to represent a video that exists but cannot yet
be played, which is why the state machine of Section~\ref{sec:database-design} is modelled
explicitly rather than inferred. The same holds after the pipeline has finished: a video that
screening held back is visible to its owner and not in the catalogue until a person approves it.

The frontend is a single page application composed of functional React components with hooks,
using React Context for authentication and theme state. Redux was considered unnecessary at
this scale, since the shared state consists only of the current user and the selected theme.

The interface is available in Vietnamese and English, selected by a control in the header and
remembered in the browser. One consequence of adding a second language is worth recording,
because it constrains the data model rather than only the presentation layer. Video categories
are stored in the database as Vietnamese strings, and the schema validates each new video against
exactly those strings, so translating a category would have made both the catalogue filter and
the upload form reject valid input. The display label and the stored value are therefore kept
apart: the client renders a translated label while always sending the original value to the API.
The same separation applies to messages the API returns, which are selected from the request's
\texttt{Accept-Language} header rather than being fixed at the point where the error is raised.

The video player is implemented as a custom component rather than relying on the browser's
native controls. The reason is that native controls cannot be extended: the browser renders its
own separate menu for playback speed and picture-in-picture, which cannot be merged with the
quality selector that HLS.js exposes. Presenting the user with two unrelated menus would be
confusing, so the component reimplements play and pause, seeking, volume, fullscreen, playback
speed, picture-in-picture, and rendition selection within a single settings menu.

The player also determines when a view is counted. Rather than incrementing the counter when
the page loads, which would allow the count to be inflated by repeated refreshes, the component
notifies the page only after playback has passed a threshold of several seconds, and the server
additionally ignores repeated reports from the same viewer within a thirty-minute window and
never counts the owner's own views.

The operations console is part of the same application, at its own address and reachable only by
staff. Its tabs are the review queue, the removed videos, appeals, audit samples, the rates, the
event log and the users, and a person sees only the tabs that the permissions of their role allow,
so an operator never sees the rates and an auditor never sees a decision button. Thumbnails of
videos under review are shown blurred until a reviewer chooses to reveal them, so that reading the
queue does not by itself expose staff to the content.
