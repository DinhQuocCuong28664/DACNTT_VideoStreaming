\chapter{System Design}
\label{chap:design}

This chapter describes the design of the system. It starts with the architecture as a whole, then
analyses in detail the two parts that make the platform a video platform: the event-driven workflow
that turns an upload into a stream, and the media design of that stream, from the FFmpeg processing
graph to the way the player chooses a quality. The remaining sections describe the database, the
API, the interface, security and content moderation.

\section{High-Level Architecture}
\label{sec:architecture}

Figure~\ref{fig:architecture} shows the deployed architecture with its real boundaries. Two
regions appear. Outside AWS are the viewer's browser, Cloudflare, which holds the domain's DNS and
runs the gateway in front of the API, and MongoDB Atlas, which holds the documents and the search
indexes. One AWS account holds everything else: compute and storage in the Singapore region, and
the two CloudFront distributions that deliver the site and the media from the edge, which read the
buckets through Origin Access Control.

\begin{sidewaysfigure}
\centering
\includegraphics[width=\textheight]{images/01-architecture-overview.png}
\caption{\textit{Architecture of the platform and its deployment boundaries; the numbered steps
are listed in the key on the left}}
\label{fig:architecture}

The account is divided into four tiers along the path of a video, with delivery beside them. The first tier serves the API. A
request from the browser reaches the Cloudflare Worker, which forwards it to the function URL of a
single AWS Lambda function running an Express application and adds a secret header, so that the
function refuses requests that bypassed the gateway (steps 1 and 2). The function reads and writes
documents in MongoDB Atlas (step 3) and keeps data that is written every few seconds, such as rate
limits, view marks, watch progress and notifications, in Amazon DynamoDB (step 4), for the reason
given in Section~\ref{sec:performance-design}. It also reads the encryption key of a video when a
player asks for it (step 5).

The second tier receives uploads and starts the processing. The browser sends the file straight to
the raw bucket with a grant from the API (step 6). The arrival of the object makes Amazon S3 emit an
event into an Amazon SQS queue (step 7), and a small function called the starter consumes the queue
(step 8) and starts one AWS Step Functions execution for the upload (step 9). From then on the
workflow owns the video: it calls short Lambda steps (step 10) and submits jobs to AWS Batch, waiting
for each one to finish (step 11).

The third tier is the serverless compute. AWS Batch runs every job as a container on AWS Fargate
(step 12), which reads the source (step 13) and writes the HLS package to the processed bucket
(step 14). The containers hold no database credentials. They report progress as events on an Amazon
EventBridge bus (step 15), and a single function, \name{status}, turns workflow states and progress
events into the processing fields of the video (steps 16 and 17). The fourth tier handles what
follows publication: when a video is published, the \name{notifier} function writes a notification
for each subscriber (step 18), and a failed video raises an alert on Amazon Simple Notification Service (SNS) (step 19).

Delivery closes the loop. The media distribution reads the processed bucket through Origin Access
Control (step 20) and serves playlists and segments only to requests that carry a valid signed policy
(step 21). The web distribution serves the single-page application from its own bucket (steps 22
and 23).

The architecture scales in each tier through a different mechanism, and each mechanism has a
ceiling that is set on purpose. The API scales by running more copies of the function, up to 80
reserved instances in production; with a pool of three database connections each, this stays well
under the 500 connections that the database tier allows. Uploads scale without any server, since
the browser writes to S3 directly. A burst of uploads becomes a burst of messages that the queue
holds, and every upload gets its own workflow execution. Compute scales by starting containers: the
Spot environment may run up to 24 vCPUs, and once it is full or Spot capacity is short, jobs overflow
to an On-Demand environment of another 24 vCPUs. Both environments scale to zero when the queues are
empty, which is what makes the platform cost nothing while idle. Delivery scales at the edge, since
the CDN caches segments and every viewer shares the same cached copies.

\section{Transcoding Workflow}
\label{sec:workflow-design}

\subsection{Ingest and Idempotency}
\label{sec:ingest}

\mbox{\texttt{raw/\{videoId\}/\{uploadVersion\}/source}} is the object key that the upload grant
fixes for the source; the grant also attaches three metadata fields: the video, the upload version
and the owner. A single POST
request carries files up to 5~GiB; larger files use a multipart upload that the API opened with the
same key and metadata, so the browser only sends parts and the API completes the upload from the part
list that S3 itself keeps. Either way, the event that starts processing is the creation of the
object, so a lost browser request cannot leave an uploaded file unprocessed.

The starter never parses the key. It reads the metadata of the object, validates it against a schema
shared with the API, and starts an execution named after the video and its upload version. The name,
\mbox{\texttt{\{videoId\}-\{uploadVersion\}}}, is what makes a duplicate harmless: Step Functions refuses a second execution with the same name~\cite{awsstepfunctions}, so when SQS delivers
the same event twice, as an at-least-once queue may, the second delivery finds the execution already
started and does nothing. This makes the whole pipeline idempotent without a table of processed
events. A message that keeps failing moves to a dead-letter queue after three receives.

\subsection{State Machine}
\label{sec:state-machine}

Figure~\ref{fig:state-machine} shows the state machine with the names of its states as defined in
the infrastructure code. \name{MarkProcessing} sets the video to \status{processing}, creates its
encryption key and confirms that the video still exists; if the owner deleted it in the meantime,
the execution ends in \name{Gone} without doing any work. \name{Probe} runs ffprobe in a Lambda
function and returns the plan: the streams, the display size after rotation, the frame rate, the
rungs of the ladder, the path and, for a long video, the chunk plan.

\begin{figure}[htbp]
\centering
\includegraphics[width=\textwidth]{images/21-state-machine.png}
\caption{\textit{State machine of the transcoding workflow, with its Catch transitions and retry
rules}}
\label{fig:state-machine}
\end{figure}

\name{Process} is a parallel state with two branches that run at the same time. The first branch
is \name{Analyse}, a Batch job that samples frames for moderation and makes the thumbnail and the
seek-preview images. The second branch encodes. A video shorter than five minutes, or one that cannot
be split safely, goes to \name{Encode}, one job that writes every rung. A longer video goes to the
chunked path: \name{Audio}, when the source has audio, then \name{Chunks}, an array job, then
\name{Stitch}. When both branches have finished, \name{Publish} checks that the master playlist
exists and sets the video to \status{ready}, or \status{scheduled} when its publication time is still
ahead, together with the result of the screening.

Failures are handled in two layers. First, each task retries the errors that may pass on their own:
a Lambda task retries service errors and throttling up to six times, waiting two seconds and doubling
the wait, and a Batch task retries a rejected submission up to five times. Every Batch job itself
has three attempts, so a Spot task reclaimed by AWS is simply run again. An error that another
attempt cannot fix, such as an unreadable source, makes the container exit with code 3, which Batch
treats as final. Second, whatever is left after the retries is caught: every task state, and the parallel
state as a whole, has a \name{Catch} that leads to \name{MarkFailed}, which sets the video to \status{error}
with the reason, tells the owner once, sends an alert and removes the temporary files. An execution
also has a timeout of 24 hours, queue time included, so no video can stay in processing forever.

\label{sec:compute-design}

six Spot slots, as Section~\ref{sec:chunked-design} explains; when the overflow is free as well,
twelve chunks run at once.

\section{Media Design}
\label{sec:media-design}

\subsection{HLS Output}
\label{sec:hls-output}

Every upload version has its own folder in the processed bucket, so a retry never mixes the files of
two runs and one signed policy for \mbox{\texttt{videos/\{videoId\}/*}} covers every version of a video.
Figure~\ref{fig:hls-output} shows what the folder contains and which tags live in which playlist.

Listing~\ref{lst:master} is the master playlist of a real video in production, a 1080p recording
with audio. Each \texttt{EXT-X-STREAM-INF} line describes one rendition, in ascending order of
bandwidth. \texttt{BANDWIDTH} is the highest bit rate of any segment of that rendition, measured from
the real segment sizes after encoding and rounded up, as RFC~8216 requires of this
attribute~\cite{rfc8216, applehlsauthoring}; \texttt{AVERAGE-BANDWIDTH} is the total size over the
total duration. \texttt{CODECS} is read from the parameters of the first segment rather than guessed,
and is left out when it cannot be read. The resolutions are not exactly 16:9 because this source is
1912 by 1080 pixels; each rung keeps the aspect ratio of the source with even dimensions.

frame rate, because segments are cut only at key frames. \texttt{EXT-X-ENDLIST} marks a complete
video on demand, so the player knows the whole timeline from the start.

The order of the uploads matters as much as the content. Segments go first, then the media
playlists, and the master playlist last, so a player can never open a master playlist whose
renditions are still incomplete. Captions, the seek-preview sprites and the thumbnail are kept out
of the playlists and loaded by the player separately, so adding a caption never rewrites a published
playlist.

\subsection{FFmpeg Processing Graph}
\label{sec:ffmpeg-graph}

Figure~\ref{fig:ffmpeg-graph} shows the processing graph of one single-path encode. The job first
copies the source to its local disk, because a long encode could outlive a presigned URL. One ffmpeg
process then reads the copy once and decodes it once; the decoder hands every frame to each output,
and each output has its own filter chain, encoder and HLS muxer. Decoding once matters because
decoding a 1080p source is a large share of the cost, and producing six renditions with six separate
processes would decode the same frames six times.

% Xoay ngang: đặt vừa bề rộng vùng chữ thì chữ dưới 6,2pt khi in.
\begin{sidewaysfigure}
\centering
\includegraphics[width=\textheight]{images/23-ffmpeg-graph.png}
\caption{\textit{FFmpeg processing graph of a single-path encode: one decode, one chain per rung}}
\label{fig:ffmpeg-graph}
\end{sidewaysfigure}

Each video chain scales the frame to the rung and sets square pixels, then encodes with x264 in the
main profile at the rung's CRF, with a maximum rate and a buffer size that cap the peak. The
remaining rules exist so that all rungs can be switched between, and they are the same on every
output. A key frame is forced at every absolute multiple of six seconds, whatever the frame rate.
The group of pictures (GOP) is six seconds of real frames, with the minimum interval set to the same
value and scene-cut key frames disabled, so the encoder never inserts an extra key frame that would
shift the next segment boundary. The pixel format is 8-bit 4:2:0, which every hardware decoder
supports, and no H.264 level is forced, so x264 chooses it from the size and rate. Each output also
encodes AAC-LC stereo audio at 128~kbit/s for 720p and above, and 64~kbit/s below. Each HLS muxer
cuts six-second segments, writes a VOD playlist and encrypts the segments with the key and IV of the
video.

After ffmpeg ends, a packaging step measures the size of every segment to compute the two bandwidth
values, reads the codec string, rewrites the media playlists in a canonical form and writes the
master playlist, which is uploaded last.

\subsection{Bitrate Ladder}
\label{sec:ladder-design}

Table~\ref{tab:ladder} lists the six rungs. Each rung combines a CRF value with a VBV cap, the
combination called Capped CRF in Section~\ref{sec:bitrate-ladder}. CRF falls by one or two steps per
rung as the resolution grows, because the same CRF looks worse on a larger screen. The maximum rates
follow the spacing of common HLS ladders, roughly doubling from rung to rung, and the buffer holds
two seconds at the maximum rate, which lets the rate vary within a segment while keeping the peak of
each segment close to the cap~\cite{applehlsauthoring, ffmpegdocs}.

The ladder is bounded by the source. A rung is named by the short side of its frame, so a portrait
video gets portrait frames without padding. Rungs smaller than the source are kept, the first rung
at or above the source is kept at the source size, and nothing larger is made, so a 360p source
gets 144p, 240p and 360p and is never upscaled. A video longer than twenty minutes that falls back to
the single path keeps only 360p, 720p and 1080p, to bound the time of one job; the chunked path
always gets the full ladder.

Figure~\ref{fig:ladder} shows what Capped CRF does with two real videos of production that went
through the same ladder. For the recording, the average bit rate stays below the cap of every rung,
reaching about three quarters of it at 1080p. For a synthetic test pattern, whose frames are easy to
predict, the encoder needs only 274~kbit/s at 1080p, a sixteenth of the cap. A fixed-bitrate ladder
would have spent the full rate on both.

\subsection{Long Videos: the Chunked Path}
\label{sec:chunked-design}

One encode of a four-hour video, even on eight vCPUs, would take hours. The chunked path in
Figure~\ref{fig:chunked-path} splits such a video into chunks that are encoded at the same time by
separate containers, then joins the results into ordinary playlists.

% Xoay ngang: đặt vừa bề rộng vùng chữ thì chữ dưới 6,2pt khi in.
\begin{sidewaysfigure}
\centering
\includegraphics[width=\textheight]{images/25-chunked-path.png}
\caption{\textit{The chunked path: plan on GOP boundaries, parallel encoding, checked join}}
\label{fig:chunked-path}
\end{sidewaysfigure}

The plan is made by the probe step and respects one rule above all: a chunk is a whole number of
six-second GOPs. Since every chunk starts at a key frame and every segment inside it is six seconds,
all rungs cut their segments at the same frames, and the joined playlists can be switched between
exactly like those of a single encode. The planner aims at about three chunks per available slot,
between 10 and 50 GOPs per chunk, so a ten-minute video becomes 10 chunks of one minute and a
four-hour video 48 chunks of five minutes. A remainder shorter than one GOP joins the previous
chunk, and the last chunk is open-ended, so an inaccurate frame count can never drop the end of the
video. Each window starts half a frame before its first frame, because a seek that lands exactly on a
frame boundary can return the previous frame, and every window ends exactly where the next one
begins.

Audio is encoded once for the whole source, by a separate job, and each chunk copies the window of
audio that matches its video. Encoding audio per chunk would leave small gaps or overlaps at every
boundary, since audio frames do not align with video frames. Each chunk child then encodes every rung
of its window with the same arguments as the single path, shifts its timestamps onto the shared
timeline of the video, and writes its segments under names that carry the chunk index. A child that
fails for good writes an abort marker, and the others stop instead of finishing useless work.

The stitch step refuses to publish anything it cannot trust. It checks that every chunk of the plan
has a result, that all rungs of a chunk cut their segments at the same instants, and that no chunk is
three or more frames longer or shorter than planned; any of these errors fails the video. Only then
does it concatenate the segment lists into one media playlist per rung, with a single key tag,
measures the bandwidth and uploads the master playlist last. The player receives an ordinary
package and cannot tell that it was encoded in pieces.

\subsection{Encryption and Playback}
\label{sec:content-protection}

Protection of the content has two layers. The first controls who can fetch the files: the processed
bucket is private and only the media distribution can read it, and the distribution serves a file
only to a request that carries a policy signed for that video. The second makes the files useless
without the key: every segment is encrypted with AES-128, and the key is released only by the API
after it checks access. Figure~\ref{fig:playback-sequence} shows how a player passes both.

\begin{figure}[htbp]
\centering
\includegraphics[width=0.95\textwidth]{images/17-playback-sequence.png}
\caption{\textit{Playback of an encrypted video: grant, signed CDN requests and key delivery}}
\label{fig:playback-sequence}
\end{figure}

\name{MarkProcessing} creates a random 16-byte key and an explicit initialisation vector (IV) for each
upload version and stores the key in a separate, private, encrypted bucket that only the transcoder
and the API can read; the workflow passes only a reference, so the key never appears in the
execution history or the logs. When a player asks to play a video, the API applies one access rule,
the same function that also decides what the watch page shows: the owner and staff may always play,
strangers learn nothing about private or unready videos, removed and held videos return 403, a
password-protected video needs an unlock token, and a members-only video needs a membership of a high
enough tier. If the rule allows playback, the API returns the master playlist address, a CloudFront
policy for \mbox{\texttt{videos/\{videoId\}/*}} valid for two hours, and a playback token, a short token
scoped to that video.

The policy travels as query parameters that the player appends to every request for the CDN, and
never to the API. Cookies were the alternative~\cite{awscloudfrontprivate}, but browsers block
third-party cookies inside an embedded player, and query parameters work everywhere. The cache key
of the distribution ignores the query, so all viewers share the same cached segments even though
each viewer's policy is different. The key endpoint accepts only the playback token, checks the
access rule again for the viewer the token was issued to, and returns sixteen raw bytes that no cache
may store. The player then decrypts each segment with AES-128 in cipher block chaining (CBC) mode, using the key and the IV of
the playlist~\cite{rfc8216}.

This design is not digital rights management. A viewer who may play a video can also save the
decrypted stream, and Widevine or FairPlay would be needed to prevent that. What it guarantees is
that no one without a grant for the video can obtain either the files or the key, even with the
exact addresses.

\subsection{Adaptive Bitrate in the Player}
\label{sec:abr-design}

The player is built on hls.js, and Figure~\ref{fig:abr-loop} shows the loop by which it chooses a
quality. Before any segment is loaded, it has no measurement and starts from a default estimate of
500~kbit/s. After each segment it measures the throughput of the download, folds it into moving
averages, scales the estimate down by a safety factor of 0.95 and chooses the highest rendition whose
declared \texttt{BANDWIDTH} fits under it~\cite{hlsjs}. The switch takes effect at the next segment
boundary. If the buffer runs low while a segment is still downloading slowly, the player abandons it
and loads a lower rendition at once rather than stalling.

\begin{figure}[htbp]
\centering
\includegraphics[width=\textwidth]{images/26-abr-loop.png}
\caption{\textit{Quality selection loop of hls.js with the settings of the player}}
\label{fig:abr-loop}
\end{figure}

Two settings of the player shape the result. \name{capLevelToPlayerSize} caps the choice at the
smallest rendition whose width or height covers the larger side of the video element on the screen,
multiplied by the pixel ratio of the display, which saves bandwidth on small windows; Chapter~\ref{chap:evaluation} shows its effect in the measurements. A choice in the quality
menu fixes the rendition and turns automatic selection off until the viewer chooses Auto again. The
loop depends on the encoding side in two ways: segments that start with a key frame at the same
instant in every rung make a switch invisible, and a \texttt{BANDWIDTH} measured as a real peak makes
the choice safe.

\section{Database Design}
\label{sec:database-design}

The documents of the platform live in MongoDB Atlas. A document store suits this data for two
reasons. A video is naturally one document whose shape grows with features: captions, chapters, the
moderation result and the counters are nested inside it and read together on every watch page, and
adding a field never needs a migration. And Atlas includes a full-text search engine in the same
cluster, so search needs no second system~\cite{mongodbsearch}. The cost of this choice is that the
database does not enforce references between collections; the design compensates with unique indexes
for every rule that must hold, and with counters that are recomputed rather than trusted.

Figure~\ref{fig:erd} shows the nine collections of the product. A channel is not a separate entity:
it is the user, identified by a unique handle. Each foreign key names the collection it refers to.

\begin{sidewaysfigure}
\centering
\includegraphics[width=\textheight]{images/04-database-erd.png}
\caption{\textit{Collections of the product in MongoDB, with their keys and unique indexes}}

The rules that must never break are enforced by unique indexes, so they hold even when two requests
race. An e-mail address and a handle belong to one account; a Google identity links to at most one
account, through a partial index that ignores accounts without one. A viewer has at most one reaction
per video and one subscription per channel, a channel has at most one active tier per level, a viewer
has one membership per channel, and every account has exactly one Watch later playlist. Where a rule
applies only to open items, such as one open report per person and video, the index is partial on
the status, so closed items do not block new ones.

A video moves through five states. \status{uploading} is set by the API when the upload is created;
\status{processing}, \status{ready}, \status{scheduled} and \status{error} are set only by the
\name{status} function of the workflow. The API changes only the fields an owner edits, so the two
writers never touch the same field. Moderation is a separate dimension with its own states,
\status{pending}, \status{approved}, \status{review} and \status{removed}, so a video can be ready
and still held for review.

Counters follow two rules. Counters of relationships, such as subscribers, likes, comments and
replies, are recomputed with \name{countDocuments} after each change, so they can never drift
from the documents they count. View and watch-time totals are sums of counted events and are
increased in place, because recounting them would itself cost database operations.

Data that is written every few seconds is kept out of MongoDB, as Table~\ref{tab:kv-tables} shows.
The free tier of Atlas throttles above one hundred operations per second, and a single playing video
reports progress every minute, so writing these records to MongoDB would spend the budget of the
whole platform on bookkeeping. Amazon DynamoDB on demand is billed per request and expires entries
by itself.

Search uses three Atlas Search indexes, the most the free tier allows: videos, channels and

\section{API Design}
\label{sec:api-design}

The API is a REST interface under the base path \mbox{\texttt{/v1}}. Requests and responses are JSON, and
every error has the same shape, an object with a machine-readable code such as
\status{email\_not\_verified} and a message, so the interface can react to the code and show the
message. Listings are paged with an opaque cursor rather than page numbers, so a list never repeats
or skips an item while new videos are published. A signed-in request carries a bearer token in the
\texttt{Authorization} header. Request bodies are limited to 64~kB, because no video data passes
through the API. Table~\ref{tab:api-routes} lists the route groups.

Two conventions follow from the design. Every route that touches a video applies the same access
rule as playback, so a private video that the requester may not see returns not-found rather than
forbidden, which does not reveal that it exists. And no route carries video bytes: an upload is a
grant around a direct transfer to Amazon S3, and playback is one call that returns a signed policy
for the CDN.

\section{Interface Design}
\label{sec:interface-design}

Figure~\ref{fig:user-flow} sets out the main paths through the application. Two of its properties
constrain the design. The first is that the home feed and the watch page are reachable without an
account, and authentication is demanded only where an action needs an identity; a visitor who
chooses to upload is sent through sign-in or registration and returned to the upload page. The second
is that the upload path does not end when the user's part ends. Once the browser has sent the file,
the interface returns control and shows the video in the creator studio with its current step and
progress, and only when the workflow marks it ready does it join the feed. The interface therefore
has to show a video that exists but cannot yet be played, which is why its states are explicit.

\begin{figure}[htbp]
\centering
\includegraphics[width=0.9\textwidth]{images/08-user-flow.png}
\caption{\textit{User flow from an anonymous visit to a published video}}
\label{fig:user-flow}

The web application is a single-page application of React components. Its pages are the home feed,
search results, the watch page, channel pages, the subscriptions feed, the library with history,
Watch later and playlists, the creator studio with upload, editing, captions, chapters, scheduling,
tiers and analytics, the settings, the staff console, the embedded player and the pages for errors.
It is available in Vietnamese and English and in light and dark themes, and its styles are plain Cascading
Style Sheets (CSS) with design tokens, without a utility framework.

The video player is a custom component built on hls.js rather than the browser's native controls,
because native controls cannot be extended: the browser has its own menus for speed and
picture-in-picture, which cannot be merged with a quality selector. The component therefore
implements play and pause, seeking with the sprite preview, volume, full screen, speed,
picture-in-picture, captions, chapters and quality in one settings menu, and resumes from the saved
position.

The staff console is part of the same application, and a person sees only the tabs their role's
permissions allow: the review queue, removed videos, reported comments, appeals, audit samples,
the rates, the event log and the users. An operator never sees the rates, and an auditor never sees
a decision button. Thumbnails of videos under review stay blurred until a reviewer reveals them, so
that reading the queue does not by itself expose staff to the content.

\section{Security Design}
\label{sec:security-design}

Authentication uses passwords hashed with bcrypt, or Google sign-in. A new password must have at
least eight characters and is refused when it is common, contains the user's own e-mail address or
handle, or appears in a known breach~\cite{nist80063b}. Sessions are bearer tokens that carry a
version number of the account; signing out, changing or resetting the password, or a Google claim of
an unverified account increments the version, which revokes every older token at once. Tokens sent by
e-mail are stored only as hashes, are valid for 24 hours for verification and one hour for a reset,
and are spent on use. Figure~\ref{fig:verification-sequence} shows how an address is verified, by the
link or by Google, and why a verified local account is never taken over by a Google sign-in.

\begin{figure}[htbp]
\centering
\includegraphics[width=0.92\textwidth]{images/18-verification-sequence.png}
\caption{\textit{Verifying the owner of an account: by the e-mailed link, or by Google sign-in with
the same address}}
\label{fig:verification-sequence}
\end{figure}

Authorisation is a table of permissions held by roles, which Table~\ref{tab:permissions} lists. The
API checks a permission, never a role name, so adding a role changes one table. The role is read
from the account on each request through a cache of 30~seconds in each instance of the function. The
instance that changes a role clears its own entry at once; the other running instances see the
change when their entry expires, so a role change reaches every instance within 30~seconds.

The API is protected in depth. The function behind it refuses any request without the secret header
that only the Cloudflare Worker adds, so its own address is useless to an attacker. Browsers may call
it only from the platform's own origins, and the key endpoint additionally refuses other origins.
Every request counts against a limit of 300 per minute per caller, and sensitive routes have tighter
ones, such as ten sign-in attempts per address in fifteen minutes; the counters live in DynamoDB so
that every copy of the function shares them. Security headers are set on every response.

Least privilege governs the infrastructure. The processing containers have no database credentials:
their role may read the raw and keys buckets, write the processed and work buckets, publish events
and call Rekognition, and nothing more. Only the \name{status} function writes processing state.
Secrets, such as the database address and the signing keys, are held in AWS Secrets Manager and read
by the functions at start-up. The protection of the content itself, private storage, signed CDN
requests and encryption, is described in Section~\ref{sec:content-protection}.

\label{sec:moderation-design}

\subsection{Automatic Screening}
\label{sec:screening-design}

The \name{analyse} job takes one frame every five seconds, at most 120 frames, so the interval
widens for long videos and the cost of a video is bounded. Each frame goes to Amazon Rekognition,
four at a time, and the labels are mapped by a shared policy to block, review or ignore, following the
label taxonomy of the service~\cite{awsrekognitionmoderation}. Labels below 60\% confidence are
treated as noise. A block label at 90\% confidence or more removes the video; any other relevant
label holds it for review. A throttled call to Rekognition is retried by the client with adaptive
back-off, up to five attempts, so a burst of uploads slows the screening rather than skipping frames. Labels such as graphic violence
in animation or illustration are lowered to review, since fiction is not the same as a recording. A
video with violence that may stay is published behind a warning that the viewer dismisses. Screening
fails closed: when no frame, or less than 80\% of the planned frames, could be analysed, the video is
held for review rather than published. Avatars, banners and custom thumbnails pass through the same
policy and are refused on any relevant label.

\subsection{Review, Appeals and Audit}
\label{sec:review-design}

An operator decides on every held or reported video with a decision, approve or remove, and a reason
code from a closed list for that decision, such as a model error, fiction, a confirmed violation or a
report upheld. Before the first human decision overrides it, the verdict of the machine is kept, and
each decision is appended to the event log with an outcome class that compares the two, as
Table~\ref{tab:outcome-classes} shows. An operator cannot change a decision taken by an
administrator. The owner of a removed or held video can appeal while no other appeal on it is open,
and an upheld appeal approves the video with the reason ``appeal upheld''.

Decisions alone cannot measure what the screening misses, because nobody reviews a video that the
machine approved and no viewer reported. The random audit fills this gap: an administrator draws a
sample of videos that the machine alone approved, an operator labels each one pass or fail, and a
failed video is removed. From these records the console computes the false positive rate of
automatic removals, the precision of holds and the false negative rate from the audit, each with a
95\% Wilson interval, which stays meaningful for small samples and rates near zero, and the sample
size beside it.

\subsection{Roles and Separation of Duties}
\label{sec:roles-design}

The roles are kept apart so that no person checks their own work. Operators decide and label;
auditors read the rates and the log but hold no permission that changes anything; administrators
manage roles and draw samples, and can act as either. The last administrator cannot be demoted, and
every change of role is logged with who made it.

\section{Performance and Scalability}
\label{sec:performance-design}

Section~\ref{sec:architecture} described how each tier scales; this section sets out the limits
that bound the scaling and how the design stays within them. The tightest are those of the free
database tier: 500 connections and one hundred operations per second.

Connections are budgeted per function, as Table~\ref{tab:connection-budget} shows. Each function
that uses MongoDB has a fixed reserved concurrency and a small connection pool per instance, so the
worst case is known in advance and stays near half of the limit. The functions of the workflow that
need no database, the starter, the probe and the stitch, open no connection at all, and idle
instances release theirs after a minute.

Operations are protected by moving every frequent write to DynamoDB (Table~\ref{tab:kv-tables}) and
by keeping the processing containers away from the database, which reduces the writes of a video
in processing to a few per minute. What remains is the work of real requests. A burst of one hundred
uploads arriving within seconds still needs several operations per upload; the free tier then slows
the requests rather than failing them, and a request refused under overload receives a status that
the client retries. Chapter~\ref{chap:evaluation} measures the effect.

On the compute side, the ceilings are those of Batch and Fargate: 24 vCPUs of Spot and 24 of
On-Demand in production, set by Terraform below the account quota of 64 of each kind so that staging
can run beside production. The two queues keep short videos ahead of chunks: the scheduler starts a
waiting job of \name{main} before any waiting chunk, so a new upload waits at most for one running
chunk to end, a few minutes, and is never queued behind all the chunks of a long video. On the delivery side, the CDN
caches segments for every viewer, because the signed policy is not part of the cache key, so the
number of viewers adds load at the edge rather than at the origin.
