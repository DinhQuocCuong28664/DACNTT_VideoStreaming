\chapter{Literature Review and Technologies}
\label{chap:literature}

This chapter first looks at how comparable platforms and reference architectures handle uploaded
video, then explains the models on which the design rests, and finally justifies the technologies
chosen for each part of the system.

\section{Related Platforms and Comparison}
\label{sec:related-platforms}

YouTube, developed by Google, is the largest video sharing platform and the functional model for
this project: channels, subscriptions, comments, playlists, paid memberships and a creator studio
with analytics are all features its users expect. Its documentation asks creators to upload an MP4
file with H.264 video and AAC audio, about 8~Mbit/s for 1080p at 30 frames per
second~\cite{youtubeencoding}, which shows that the platform treats the upload as a high-quality
master and produces its own delivery formats from it. Vimeo, developed by Vimeo, Inc., targets
creators and businesses rather than a mass audience. It accepts H.264, H.265 or ProRes and
recommends encoding the upload at a constant rate factor of 18 or below~\cite{vimeocompression},
again a quality-targeted master from which the platform builds its own renditions. Neither
platform documents its internal pipeline, and neither can be self-hosted, so they serve here as the
reference for features and user expectations rather than for architecture.

Netflix offers the most thoroughly documented pipeline. Its video processing was rebuilt as
independent services, for inspection, encoding and quality measurement, on a platform called
Cosmos~\cite{netflix2024microservices}. Cosmos is layered: an API tier receives requests, a workflow
tier orchestrates the steps, and a serverless compute tier performs the media work, the tiers being
connected asynchronously~\cite{netflix2021ves}. Two ideas from this design are applied here at a
much smaller scale. The first is the separation between a workflow that owns the job and the compute
that performs each step. The second is chunk-based encoding, in which many workers encode parts of
the same title in parallel instead of one worker encoding it from start to end.

Amazon Web Services publishes the Video on Demand on AWS solution, a reference architecture built
entirely from managed services~\cite{awsvod}. An upload to Amazon S3 starts an AWS Step Functions
workflow, AWS Elemental MediaConvert produces the renditions, and Amazon CloudFront delivers them.
The architecture of this project follows the same overall shape, a workflow engine that owns each
video, but replaces MediaConvert with FFmpeg in containers on AWS Batch and Fargate. This
substitution is the central trade-off of the project. MediaConvert needs almost no operational
effort but is billed per minute of output and fixes what the encoder can do, whereas a
self-packaged container is cheaper per unit of work and fully controllable, at the price of
maintaining the image and handling failures in the team's own code.

\section{Core Models and Principles}
\label{sec:core-models}

\subsection{Serverless Containers}
\label{sec:serverless-containers}

A serverless container runs a container image without the developer provisioning or managing the
virtual machines underneath, and is billed for the time it runs rather than for capacity kept
available. AWS Fargate provides this model, and AWS Batch can schedule jobs onto it through compute
environments of type \texttt{FARGATE} or \texttt{FARGATE\_SPOT}~\cite{awsbatchfargate}. Spot
capacity uses spare AWS capacity at a lower price and may be reclaimed; this project therefore
places a Spot environment first and an On-Demand environment second behind the same job queue, so
that jobs run on Spot whenever it is available and overflow to On-Demand otherwise.

Figure~\ref{fig:compute-models} contrasts this model with an always-on server for a workload of
three hundred five-minute videos per month. Measured on the final configuration, a 1080p video costs
about 5.5 vCPU-seconds of encoding work per second of source, so the month needs about 138
vCPU-hours of real work. An always-on instance with eight vCPUs, the size of one encoding job, is
billed for all 5,840 vCPU-hours of the month and is busy for about 2.4~percent of them. Its capacity
is also a hard ceiling: a burst larger than one instance can handle must wait. With serverless
containers, no compute exists between uploads, a container starts for each job and stops when the
job ends, and a burst is absorbed by the queue up to the configured maximum number of vCPUs. Priced
at the On-Demand rate, the same month costs about 8.47~USD instead of 286.16~USD;
Section~\ref{sec:cost-analysis} gives the full calculation.

A function platform such as AWS Lambda is the more common serverless choice, so its rejection for
encoding needs a reason. A Lambda invocation can run for at most fifteen
minutes~\cite{awslambdaquotas}, while encoding a long video takes far longer, and a measurement
study of serverless video processing found that the cost-efficient memory setting depends on the
task and even on the content, with differences of up to 498~percent between
settings~\cite{nossdav2019video}. Fargate lets vCPU and memory be chosen explicitly for each job.
Lambda remains the right tool for the short steps of the pipeline, such as reading the source
metadata, starting the workflow or writing the final playlists, and the project uses it there. The
known weakness of containers is start-up latency; a systematic review reports that pulling the image
dominates the cold start of container-based functions~\cite{coldstart2023}, which motivates the small
multi-stage image described in Chapter~\ref{chap:implementation}.

\subsection{Event-Driven Architecture and Workflow Orchestration}
\label{sec:event-driven}

In an event-driven architecture, work moves through the emission and consumption of events rather
than through direct calls. The AWS Serverless Applications Lens describes such systems as event
sources, routers and destinations connected by durable queues and explicit data
contracts~\cite{awsserverlesslens}. In this project, the event source is Amazon S3: when an upload
completes, S3 emits a notification that is placed on an Amazon SQS queue. The queue absorbs bursts,
because a hundred simultaneous uploads become a hundred messages that are consumed as fast as the
downstream steps allow, and a dead-letter queue isolates a message that keeps failing instead of
retrying it forever. Because a queue delivers each message at least once, never exactly once, every
consumer must make a repeated delivery harmless.

A queue alone does not say what happens to a video after the first step. AWS Step Functions fills
this gap: it runs state machines whose states are tasks, choices, parallel branches and maps, and a
Standard workflow can run for up to one year while keeping the history of every
step~\cite{awsstepfunctions}. Its integration with AWS Batch can submit a job and wait until the job
finishes~\cite{awssfnbatch}, so the workflow, not the container, decides what runs next, how often a
failed step is retried and what happens when retries are exhausted. AWS Batch array jobs complete the
picture for long videos: one submission creates between 2 and 10,000 child jobs that share a
definition and differ only by their index~\cite{awsbatcharray}, which is how one video is split into
many chunks without one call per chunk. Chapter~\ref{chap:design} draws the resulting state machine.

\subsection{HTTP Live Streaming and Adaptive Bitrate}
\label{sec:hls-abr}

HLS delivers a video as a master playlist that refers to several media playlists, each listing the
segments of one rendition~\cite{rfc8216}. For each rendition the master playlist declares a
\texttt{BANDWIDTH}, the peak bit rate the client must sustain, and optionally an
\texttt{AVERAGE-BANDWIDTH}. Apple's authoring specification, which most deployments follow, asks for
segments of nominally six seconds, for every video segment to start with an IDR frame, and for
\texttt{BANDWIDTH} to be the largest peak segment bit rate~\cite{applehlsauthoring}.

Figure~\ref{fig:hls-abr} shows the artefacts produced from one source and the order in which a
player retrieves them. The player first fetches the master playlist, a few hundred bytes, chooses a
rendition from the declared bandwidths and its own throughput estimate, and only then requests that
rendition's playlist and segments. Because every rendition is cut on the same boundaries and each
segment starts with a key frame, the player can change rendition at any segment boundary without
interrupting playback. The player used here, hls.js, estimates throughput as an exponentially
weighted moving average of segment downloads and scales the estimate down by a safety factor
before choosing~\cite{hlsjs}. For the transcoding side, the consequence is that the work grows with
the number of renditions, since each one is encoded separately even though the source is decoded
only once.

\subsection{The Bitrate Ladder and Capped CRF}
\label{sec:bitrate-ladder}

The set of resolution and bit rate pairs offered is called the bitrate ladder. Netflix showed that
the best ladder depends on the content and that the ideal operating points lie on the convex hull
of the quality against bit rate curve~\cite{netflix2015pertitle}; encoding each shot separately
under a perceptual quality metric reduced bit rates by 28 to 38~percent at the same quality in its
measurements~\cite{netflix2018dynamic}. Such optimisation requires many trial encodes per title,
which is beyond the budget of this project.

This project instead combines a fixed ladder with quality-targeted encoding. The x264 encoder
used through FFmpeg~\cite{ffmpegdocs} can work at a constant rate factor (CRF), which keeps
perceptual quality roughly constant and lets the bit rate rise and fall with the complexity of each
scene; Vimeo's recommendation to upload at CRF 18 or below rests on the same
idea~\cite{vimeocompression}. Pure CRF has no upper bound, however, which would make the
\texttt{BANDWIDTH} of a rendition unpredictable. Adding a maximum rate and a decoder buffer size,
the video buffering verifier (VBV), caps the peak while CRF still controls quality below the cap.
This combination, called Capped CRF, gives static scenes fewer bits and complex scenes more, up to a
known limit per rung. Each video receives only the rungs its source resolution can fill, from 144p
to 1080p, so nothing is upscaled. Chapter~\ref{chap:design} lists the rungs and their parameters.

The API is written in TypeScript on Node.js~22. Its work is almost entirely input and output:
checking a token, reading a document, signing a URL. The heavy computation is delegated to the
containers, so the event loop of Node.js suits it, and one language across the API, the Lambda
steps, the transcoder and the web client lets them share a single package of schemas that both the
producer and the consumer of each event validate. Running the API as one Express application inside
one Lambda function keeps the code of an ordinary web server while removing the server: AWS starts
as many copies as there are concurrent requests and none when there are none.

MongoDB Atlas holds the documents: users, channels, videos, comments, playlists and moderation
records. Its search feature provides full-text search embedded in the same database~\cite{mongodbsearch},
which avoids running a separate search cluster. The project uses the free tier of Atlas, whose limit
of one hundred operations per second would be reached by data written on every few seconds of
playback, such as watch progress, view marks and rate-limit counters. These are therefore kept in
Amazon DynamoDB, billed per request and able to expire entries on its own.

Playback uses hls.js rather than the browser's native HLS support even in browsers that have it.
Access to the processed files is granted by a signed policy that must be appended to every playlist
and segment request, and only hls.js lets the application change each request before it is sent.
Chapter~\ref{chap:design} explains this access scheme in detail.
