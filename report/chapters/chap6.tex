\chapter{Deployment and Evaluation}
\label{chap:evaluation}

This chapter describes the deployed system and its interface, then evaluates it: playback quality
as a viewer experiences it, transcoding latency, the chunked path for long videos, behaviour under a
burst of uploads, and the monthly operating cost. It ends by setting the non-functional requirements
of Section~\ref{sec:nonfunctional-requirements} against this evidence. Every figure was measured on
the live deployment or on a staging environment with the same configuration.

\section{The Deployed Environment}
\label{sec:deployed-environment}

The frontend is a single-page application served from an Amazon S3 bucket through its own
CloudFront distribution. The backend API runs as a Node.js process on an Amazon EC2 instance, behind
nginx for TLS termination and a process manager that restarts it on failure. Media is served from a
third hostname, the video distribution, whose origin is the processed-content bucket and which
admits a request only when it carries a valid Signed Cookie. Cloudflare provides DNS and edge TLS
for the two application hostnames, MongoDB Atlas holds the database, and the transcoding tier of
Chapter~\ref{chap:implementation}, made of the SQS queue, the Lambda submitter and AWS Batch,
occupies no capacity between jobs.

A scheduled health check calls the public API every five minutes and publishes a metric that an
alarm watches, so the service is monitored rather than only the instance hosting it. The instance is
the only component that costs money continuously, and it can be stopped and restarted without losing
its environment file, its TLS certificates or its public address.

\section{Quality of Experience Evaluation}
\label{sec:qoe-evaluation}

The playback measurements were taken in September 2026, when the bitrate ladder had three rungs,
360p, 720p and 1080p; it was extended to six rungs on 7 October 2026
(Section~\ref{sec:transcoder-impl}). The findings below do not depend on the number of rungs.

Time to first frame (TTFF) is measured by a script that fetches the master playlist, then a
rendition playlist, then the first media segment, and records the time of each stage. Each
measurement is repeated twenty times, because one sample means little when network latency varies
and the first request is usually a cache miss. Measured directly against the S3 bucket, before the
CDN was deployed, the median TTFF was 251.52~ms. This origin latency is the baseline for the CDN
measurements; its statistics are in Table~\ref{tab:ttff-results} (Appendix~\ref{app:measurement-tables}).

\subsection{Time to First Frame Through the CDN}
\label{sec:cdn-measurement}

Through the CDN every request must carry a Signed Cookie, so the script first requests cookies from
the playback-authorisation endpoint and attaches them to all three stages, as a browser does.
Figure~\ref{fig:ttff-cdn} compares the three delivery configurations.

\begin{figure}[H]
\centering
\includegraphics[width=\textwidth]{images/11-chart-ttff-cdn.png}
\caption{\textit{Median time to first frame in three delivery configurations, and the median of each stage where it was measured}}
\label{fig:ttff-cdn}
\end{figure}

\noindent\textit{Note: $n=20$ per configuration. Through the Ho Chi Minh City edge, the eighteen
samples that hit the cache at all three stages have a median of 107.57~ms. The file of the 727.69~ms
run was overwritten by the later run, so its stages are not shown. Full statistics are in
Table~\ref{tab:ttff-cloudfront} (Appendix~\ref{app:measurement-tables}).}

The first run through the CDN gave a median of 727.69~ms, 2.9 times slower than the origin it was
meant to accelerate. Caching was not the cause: nineteen of twenty samples were edge hits, and the
single miss took 4655~ms. Every response carried \texttt{X-Amz-Cf-Pop: MRS53}, an edge in Marseille,
France, because both distributions used \texttt{PriceClass\_100}, the cheapest class, which serves
only from North America and Europe. Every request from Vietnam, where the users are, therefore
crossed to Europe and back.

Changing both distributions to \texttt{PriceClass\_200}, which includes Asia, moved delivery to
\texttt{SGN50} in Ho Chi Minh City. The median fell to 110.32~ms, 6.6 times faster than through
Marseille and 2.3 times faster than the S3 origin. The two playlists, small cached files, now take
single-digit milliseconds, and the segment, the only stage with a real payload, takes most of the
time. The fault was invisible to every check except a measurement taken from where the users are:
the configuration was valid, the cache hit rate was high and every request succeeded.

\label{sec:multiregion-measurement}

Because one vantage point had hidden that fault, the probe was deployed as an AWS Lambda function in
five regions, run twenty times in each, and deleted afterwards. Figure~\ref{fig:ttff-regions} shows
the result.

\begin{figure}[H]

\includegraphics[width=\textwidth]{images/12-chart-ttff-regions.png}
\caption{\textit{Median time to first frame by client location, before and after \texttt{PriceClass\_All}}}
\label{fig:ttff-regions}
\end{figure}

\noindent\textit{Note: milliseconds, $n=20$ per location and configuration. A location with one bar
was measured in one configuration only. The Ho Chi Minh City bar is the consumer-connection

Table~\ref{tab:ttff-multiregion} (Appendix~\ref{app:measurement-tables}).}

Under \texttt{PriceClass\_200}, four locations clustered between 55 and 60~ms, each served by an edge
in its own region. S\~{a}o Paulo was the exception: it was served by \texttt{CPT51} in Cape Town at a
median of 1196~ms, because this price class excludes South America and Oceania. Both distributions
were therefore moved to \texttt{PriceClass\_All}. Brazil is now served by \texttt{GRU1} in S\~{a}o
Paulo at 36.79~ms, a thirty-two-fold improvement, and Sydney by \texttt{SYD3} at 52.30~ms, while the
two control locations moved by less than 4~ms.

The system has no users in South America or Oceania, so this change met no existing need. It was
adopted because it costs nothing in practice: the CloudFront free tier covers one terabyte of transfer
and ten million requests a month, far above this deployment's traffic. If traffic ever exceeds that
allowance, this setting should be revisited first, since those regions have the highest
per-gigabyte rates.

These probes ran inside AWS regions over well-provisioned paths, which is why they report about
55~ms while the consumer connection in Ho Chi Minh City reports 110~ms to an edge in the same city.
The figures therefore measure edge proximity under favourable conditions, not what a home viewer
sees; on this evidence the last mile costs roughly a factor of two.

\subsection{Playback Under Constrained Bandwidth}
\label{sec:qoe-playback}

Rebuffering, bitrate switches and the bitrate a viewer receives exist only while a player is
playing, so HTTP requests alone cannot measure them. The harness written for this drives the
deployed watch page in headless Chromium with Playwright, reads the \texttt{waiting},
\texttt{playing}, \texttt{ended} and \texttt{resize} events of the \texttt{<video>} element, and caps
bandwidth through the Chrome DevTools Protocol. Startup buffering is excluded from the rebuffering
ratio, the first rendition choice is not counted as a switch, and the average bitrate is computed
from the bytes received, weighted by the time each rendition was on screen. Each profile discards
two warm-up runs before recording five, because with one warm-up the first slow 3G run took
26.04~s to start against about 1.90~s for the others.

The correction helps only on fast 3G. There the worst startup delay falls from 16.81~s to 2.39~s,
mean rebuffering halves and the stalled runs drop from two to one. The price is a 15\% lower average
bitrate and a rise in the median number of switches from one to four, as the player now adapts
instead of holding a level it cannot carry. The unthrottled profile is a control and does not change:
its startup maximum moved from 3.29 to 5.22~s through one slow run, with rebuffering at zero in both
rounds. Slow 3G does not change either, to within 0.02 percentage points, because even the lowest
rung, with an actual peak of 637~kbit/s, exceeds its 512~kbit/s ceiling. A manifest cannot help a
player that has no lower rung to choose, so the remedy for this case would be a lower rung.

Three limits apply to these results. The peak that the harness observes is a lower bound, because
it sees only the segments the player fetched. The profiles ran in sequence, so the edge cache state
is confounded with profile order for startup delay, which likely explains why fast 3G started faster
than the unthrottled profile. And the harness exports its event log in the input format of the ITU-T
P.1203 model but computes no MOS score, so none is claimed.

\subsection{Effect of Content Complexity}
\label{sec:qoe-multisource}

The results above come from one source video, so they could describe that file rather than the
system. The attribute that plausibly governs playback is visual complexity, measured here as the
bitrate of a sixty-second excerpt encoded at constant quality (CRF~23): at constant quality the
encoder lets the bitrate follow the content. Three sources measured 151, 405 and 2298~kbit/s, a
spread of 15.2 times, and are called low, medium and high below. Each source ran under all three
profiles before the next began, so the effect of profile order cancels when sources are compared.

element, scaled by the device pixel ratio.

\section{Transcoding Pipeline Performance}
\label{sec:pipeline-evaluation}

Pipeline latency runs from the end of the upload to the moment the record reaches \texttt{READY},
which is the interval a user actually waits. It includes the S3 event delay, queueing in SQS,
container start-up on Fargate, FFmpeg and the upload of the results. These measurements predate the
six-rung ladder and chunked transcoding: one container per video produced 360p, 720p and 1080p, the
configuration that Section~\ref{sec:chunked-evaluation} later compares against. The job definition
revision that each job ran was checked afterwards, so the allocation of every row is confirmed
rather than taken from the label the script recorded.

The realtime factor stays between 3.70 and 3.97 across a thirteen-fold range of duration, so at fixed
compute the pipeline time grows linearly with duration. The three 100~MB runs, 346.32, 539.80 and
541.28~s, show no cold-start pattern, since the first was the fastest; at this scale the variation of
Fargate Spot capacity appears to dominate. The 500~MB and 1~GB sizes were measured once each, because
each run occupies 30 to 100 minutes of AWS Batch time.

Raising the container from 1~vCPU and 2~GB to 4~vCPU and 8~GB reduced the mean pipeline time from
475.80~s to 115.56~s for 100~MB (three runs each), and from 5917.03~s (one run) to 1078.70~s for 1~GB
(two runs, 1080.29 and 1077.10~s), speedups of 4.12 and 5.49 times. Both exceed the four times that the vCPU count alone
could explain. Amdahl's Law bounds the speedup below the resource ratio, because parts of an encoder
such as entropy coding and rate control do not parallelise, and multi-threaded H.264 studies report
this sub-linear pattern: 1.97, 3.96 and 7.71 times at 2, 4 and 8 threads~\cite{sankaraiah2014macroblock},
and 4.7 to 8.6 times across six Cell SPEs~\cite{chen2011taskbased}.

Two confounds explain the excess. Memory rose from 2 to 8~GB at the same time as the vCPU count, and
the 1~vCPU baseline is unstable: its three 100~MB runs spread by 56.3\%, against 24.0\% at 4~vCPU. The
speedup is therefore 3.29 comparing the fastest runs, 4.12 the means, 4.15 the slowest runs and 4.86
the medians. The data support a reduction of roughly four times, but not a precise scaling law. Cost
per video is unaffected either way: Fargate bills per vCPU-second, so four times the rate for a
quarter of the time leaves the charge per video about the same, and the 4~vCPU configuration buys a
much shorter wait at almost no extra cost.

\section{Chunked Transcoding of Long Videos}
\label{sec:chunked-evaluation}

A single container transcodes at a roughly constant fraction of the video's runtime, and one AWS
Batch job is limited to two hours. A five-minute video took 26.7 minutes as a single job, which
extrapolates to about twenty-one hours for four hours of content, so the requirement to accept videos
of four hours or more needs the chunked path of Section~\ref{sec:chunked-design}. The packets of the
produced renditions were checked for gaps and overlaps at every chunk boundary, and the check passed
in every run below.

The measurements ran in the staging environment, which has the same container image, job definitions
and compute settings as production but its own database and buckets. Capacity is the Fargate vCPU
quota: 8~vCPU of Fargate Spot, which is the production quota, or 16~vCPU when an On-Demand
environment of 8~vCPU was attached behind it. Each chunk runs in a 4~vCPU, 8~GB task, the size chosen
in Figure~\ref{fig:chunk-config}. Latency runs from the end of the upload to \texttt{READY}. The
25-minute source is a 1080p H.264 file of 2.75~GiB with AAC audio. The four-hour source repeats a
1,600-second 1080p test pattern nine times with a 128~kbit/s tone, and was uploaded with S3 multipart,
as the browser does for files larger than 512~MiB.

\section{Load Testing}
\label{sec:load-testing}

The load test checks that a burst of uploads loses no work and that AWS Batch runs it at its
configured concurrency. Fifty virtual users perform one hundred upload cycles, each of which
initiates an upload, sends the file to S3 with the pre-signed URL and confirms it; the job queue is
then polled every 25 seconds until it is empty. The compute environment allowed 8~vCPU and each job
1~vCPU, so at most eight jobs could run at once.

\subsection{Queue and Admission Under Burst Load}
\label{sec:load-cross-validation}

The burst test evaluates the queueing, ingestion, and admission behaviour of the event-driven architecture under sudden traffic surges. Fifty virtual users execute one hundred upload cycles concurrently, driving the upload authorisation endpoint, direct-to-S3 storage transfer, Amazon S3 event notification, Amazon SQS buffering, and AWS Batch job submission. The test was conducted using two independent load generators, a custom Node.js script and k6, ensuring that observations reflect actual system behaviour rather than generator-side bottlenecks (Table~\ref{tab:load-crossvalidation}).

All one hundred upload cycles succeeded with both tools. The Node.js script completed 15.52 cycles per second, with a mean of 2388.52~ms and a 95th percentile of 3317.79~ms per cycle. k6 times each individual request rather than the complete three-request cycle: its mean of 670.03~ms over 300 requests corresponds to 2010.09~ms per cycle, within 15.8\% of the Node.js measurement, while its steady-state rate of 17.24 cycles per second closely matches the 15.52 figure.

The two independent tools agree on every observation of the queue. Immediately following the arrival burst, 92 jobs were queued in the \texttt{RUNNABLE} state and 8 had been admitted into execution, while Amazon SQS retained zero messages, confirming that the AWS Lambda submitter drained events into AWS Batch within seconds. SQS successfully buffered every unit of work submitted faster than the compute environment could process it, and AWS Batch admitted work up to, and never exceeding, its resource ceiling.

\subsection{Pipeline Throughput and Backlog Drain Under Real Workload}

To evaluate sustained end-to-end processing throughput and verify that all submitted media files successfully complete the full transcoding pipeline, the load scenario was executed with real H.264 video clips in a burst of one hundred simultaneous submissions. \subsection{Serverless Backend Concurrency and Latency Evaluation}
\label{sec:backend-evaluation}

The initial load test revealed a severe concurrency bottleneck in the monolithic Amazon EC2 baseline: when fifty virtual users submitted requests simultaneously, the single Node.js event loop became saturated, driving the mean request latency to 2388.52~ms and the 95th percentile to 3317.79~ms, with maximum response spikes exceeding 6.13 seconds in the k6 test suite. Furthermore, the virtual machine represented a single point of failure (SPOF) with persistent idle costs.

\section{Cost Analysis}
\label{sec:cost-analysis}

The comparison sets an always-on Amazon EC2 instance running FFmpeg against the serverless container
architecture, for three hundred videos a month averaging five minutes each. The processing effort
comes from the measurements of Section~\ref{sec:chunked-evaluation}: a 25-minute video used 6,363
vCPU-seconds at the best configuration and a four-hour video 15.1 vCPU-hours, about 0.35 vCPU-hours
per five minutes of video, so the month needs about 105 vCPU-hours. In other words, encoding one second
of 1080p video takes about four vCPU-seconds.

Prices are the ap-southeast-1 list prices read from the AWS Price List API on 15 October 2026:
0.05056~USD per Fargate vCPU-hour and 0.00553~USD per GB-hour, which is 0.0616~USD per vCPU-hour with
the 2~GB per vCPU of the chunk tasks. Spot capacity is taken at 30\% of that, 0.0185~USD, since AWS
publishes discounts of up to 70\%; the real Spot price varies with demand.

the architecture controls is 97.5\%.

The saving comes entirely from removing idle capacity. Beyond the transcoding cluster, hosting the backend API on an always-on \texttt{t3.small} EC2 instance would contribute an additional \.58 monthly (\.98 compute plus \.60 for the 16~GB EBS root disk) even during zero-traffic idle periods. Transitioning the API to AWS Lambda completely eliminates this baseline expenditure: with monthly traffic estimated at 50,000 API calls, usage remains comfortably within the AWS Always Free Tier (1,000,000 requests and 3,200,000 seconds of compute monthly), yielding an operational cost of exactly \.00 for backend compute. The always-on instance offers 2,920
vCPU-hours a month, four vCPUs for 730 hours, while the work needs about 105 of them, a utilisation of
roughly 3.6\%. The advantage is therefore not universal: as sustained utilisation rises, per-second
Fargate billing approaches and then exceeds the cost of a reserved instance. The architecture suits
bursty workloads, which user-generated video uploads are.
