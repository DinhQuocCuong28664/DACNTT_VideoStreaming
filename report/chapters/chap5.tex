\chapter{Development and Testing}
\label{chap:implementation}

This chapter describes how the design of Chapter~\ref{chap:design} was built. It presents the
structure of the code, the implementation of the processing pipeline, the API and the web
application, the infrastructure code and the delivery pipeline. It then records the problems met
while building the system and how each was solved, and ends with the automated tests.

\section{Repository Structure}
\label{sec:repo-structure}

The whole system lives in one repository organised as npm workspaces, so that a change to a
contract shared by two parts is made, type-checked and tested in one commit.
Table~\ref{tab:workspaces} lists the workspaces and where each one runs. Every workspace except
\name{infra} is written in TypeScript and runs on Node.js~22; each deployable part is bundled into
a single file with esbuild, so a Lambda package or the container image carries no
\name{node\_modules} folder.

The \name{shared} package is what keeps the event-driven parts consistent. The starter function
validates an S3 event against the same schema that the API used when it wrote the object metadata,
and the status function accepts a progress event only if it matches the schema that the container
used to emit it. A field renamed on one side therefore fails the type check of the other side before
it can fail in production.

\section{Processing Pipeline}
\label{sec:transcoder-impl}

\subsection{Workflow Functions}
\label{sec:functions-impl}

The seven functions are small and each has its own role with only the permissions it needs. The
starter turns each record of an SQS batch into one Step Functions execution named after the video and
its upload version, and reports only the failed records back to SQS, so one bad message does not make
the whole batch return to the queue. The probe function runs \name{ffprobe} from a Lambda layer
that holds a static build of the tool, plans the job with the functions of \name{shared} and stores
the plan in the work bucket; the state machine receives only a summary, which keeps the execution
history small. The status function is the only writer of processing state: it moves a video through
\status{processing}, \status{ready} or \status{error}, folds progress events from the two parallel
branches into one percentage that never goes backwards, and announces a published video exactly once.
The stitch function joins the chunk playlists and writes every media playlist before the master
playlist, as Section~\ref{sec:hls-output} requires. The last three functions serve the API: the
notifier writes a notification for each subscriber and mails those who opted in, the roll-up adds the
viewing heartbeats of the previous hours into daily analytics, and the reconciler removes drafts whose
upload never finished.

\subsection{Transcoder Image}
\label{sec:image-impl}

The four roles share one container image built in stages. The build stage bundles the entry points;
the runtime stage holds only Node.js, a static FFmpeg build and the bundle, runs as a non-root user and
measures 136~MB compressed. Both base images are pinned by digest, so two builds of the same commit
produce the same image. \name{ffprobe} is left out of the runtime image because probing runs in
Lambda. Every Fargate task pulls the image before it starts, and pulling dominates the start-up time
of a container~\cite{coldstart2023}, so its size bears directly on how quickly a job begins. A separate
\name{smoke} stage adds \name{ffprobe} and a test program on top of the runtime stage; it is used
only by the delivery pipeline of Section~\ref{sec:cicd}, and because the runtime stage is the last one
in the file, a build without an explicit target can never ship the test tools.

The encode and audio roles download the source to the task's disk before they start FFmpeg. Reading
it through a pre-signed URL would avoid the copy, but such a URL is signed with the task's temporary
credentials and stops working when they expire, which can happen during an encode of several hours.
The chunk role reads only its own time range, which is short, so it does read through a pre-signed
URL.

\subsection{Failure Handling Inside a Job}
\label{sec:job-failure-impl}

A failed job ends with one of two exit codes, because the retry rule of
Section~\ref{sec:compute-design} depends on it. A failure that would repeat with the same input, such
as a file FFmpeg cannot decode or a plan that fails validation, ends with exit code 3, which Batch
does not retry; every other failure, including a Spot reclaim or a network error, ends with a code
that Batch retries. The FFmpeg runner keeps the last lines of the error output in the failure reason
and reports a process killed by a signal as such, so an operator can tell a reclaimed Spot task from
a broken file.

The encode guard stops a run that cannot finish in time as soon as that is clear, instead of letting it
use the Fargate task until the timeout. During the run it projects the total time as the video
duration multiplied by the ratio of elapsed time to encoded position. It gives no verdict during the
first 120~seconds or before 30~seconds of video are encoded, and it stops the run only when the
projection has stayed above 90\% of the job budget for 180~seconds, so one slow scene never ends a
healthy job.

\section{API and Web Application}
\label{sec:backend-impl}

The API is one Express~5 application adapted to Lambda with \name{serverless-express}. It is
organised by feature: authentication, uploads, videos, community, channels, library, studio,
discovery and moderation each register their own routes, and reach storage, the CDN signer, mail, the
scheduler, image screening and search through service interfaces. In production these interfaces are
backed by AWS and Atlas; in the tests they are backed by in-memory implementations, which lets a test
run a whole route without the network. Every request body is validated with a zod schema, and every
error leaves the API in the shape \mbox{\texttt{\{error:\{code,message\}\}}} of Section~\ref{sec:api-design}.
The rule that decides whether a user may see or play a video is one function, called by every route
that exposes a video, its comments, its playlist or its key.

A new instance does as little as possible before its first request: it reads its secret from Secrets
Manager and opens the database connection, and both are kept for the life of the instance. Indexes
are created by a separate maintenance action, run once after each deployment
(Section~\ref{sec:challenges}). The Cloudflare Worker in front of the Function URL replaces the host
header with that of the function, removes any \texttt{X-Origin-Verify} header sent by a client and
adds the secret one, so the API refuses every request that did not pass through Cloudflare, and
trusts the client address in \texttt{CF-Connecting-IP} only on such requests.

The web application is written in React~19 with React Router and i18next for its two languages.
Styling uses vanilla CSS with custom properties for the light and dark themes, without a utility
framework. Two parts of its client code carry most of the robustness. The HTTP client retries a
request that receives 429 or 503 up to three times, after about 0.5, 1 and 2~seconds
with random jitter, and follows a \texttt{Retry-After} header capped at ten seconds; a retry is safe
even for a POST, because both answers are given before any handler runs. The upload client
sends the parts of a multipart upload, retries a failed part with a newly signed URL, and stops at once
when the viewer cancels.

\section{Infrastructure as Code}
\label{sec:iac}

All cloud resources are described with Terraform in eleven modules, listed in
Table~\ref{tab:terraform-modules}, and three environments. The \name{shared} environment holds what
every environment uses once: the VPC and the image registry. The \name{staging} and \name{prod}
environments compose the modules with their own names (prefix \name{zelos-staging} or
\name{zelos-prod}), capacity ceilings and hosts. Each environment keeps its state in its own key of
an S3 bucket, with a DynamoDB table as lock, so two applies can never write the same state at once.
Every resource carries the tags \name{Project}, \name{Stack}, \name{Environment} and
\name{ManagedBy}.

An environment declares three providers: AWS in the Singapore region, which also manages
CloudFront because CloudFront is a global service, AWS in \name{us-east-1}, the only region where

receive the first two through aliases, so the account and the regions they use are chosen by the
environment and not written into the modules. The transcoder image is selected with a variable that holds the commit of the image
and has no default value, so a production apply cannot fall back to an untested image.

\section{Continuous Integration and Deployment}
\label{sec:cicd}

Two GitHub Actions workflows check every push and pull request, as shown in the upper part of
Figure~\ref{fig:cicd}. The first lints all workspaces, type-checks them, runs the unit tests and builds
every deployable part; it then builds the \name{smoke} stage of the image and runs real FFmpeg in it,
and checks the formatting and validity of the Terraform code without access to any account. The second
is the security gate: Gitleaks scans the whole history for secrets, Trivy scans the dependencies and
\name{eslint-plugin-security} analyses the code statically. The security jobs are required checks of
the rule that protects the main branch, so a pull request cannot be merged while one of them fails.

\begin{figure}[htbp]
\centering
\includegraphics[width=\textwidth]{images/03-cicd-pipeline.png}
\caption{\textit{The checks run by GitHub Actions on every push and pull request, and the deployment
steps run after a merge}}
\label{fig:cicd}
\end{figure}

The dependency scan has two tiers. It reports every critical and high finding without failing, and
fails only on a critical finding that already has a fix. Most high findings come from transitive
dependencies with no patch yet, so a gate that failed on all of them would fail for reasons the team
cannot act on and would soon be ignored. The scan of the Terraform code is stricter and fails on any
high or critical misconfiguration, because every such finding can be fixed in the project's own code.
Each action that runs Trivy is pinned to a release commit rather than a branch, so
a change in another repository cannot alter what runs in the pipeline.

The smoke test runs the encoding commands of the deployed image on generated sources and checks the
result as a player would. It encodes a 40-second source on the single path and a 75-second source on
the chunked path, decrypts and decodes every rung, and checks the codec strings, the segment
durations, the rising bandwidth values and the absence of repeated audio packets at chunk boundaries;
a third case checks the preview sprites. In thirteen checks it exercises what the unit tests cannot,
namely the behaviour of FFmpeg itself.

Deployment is deliberately not automated. No workflow holds AWS credentials; the steps in the lower
part of Figure~\ref{fig:cicd} run from the operator's machine, and each is approved before it runs.
The API and the functions are bundled; the image is built and pushed to the registry with the commit
as its tag; Terraform applies the environment with that tag; the maintenance action creates the
indexes; and the web files are uploaded, hashed assets first and the entry page last, so the new
entry page never refers to a file that is not there yet, after which the distribution is invalidated.
The end-to-end tests of Section~\ref{sec:testing} then run against the deployed environment. A change
is applied to \name{staging} and checked there before it is applied to \name{prod}.

\subsection{One Policy for the Processed Bucket}

A bucket has exactly one policy, but two modules need a statement in the policy of the processed
bucket: \name{storage}, which refuses every request without TLS, and \name{cdn}, which lets its
distribution read the segments. If both wrote the policy, each apply of one would remove the
statement of the other, and the bucket would alternate between refusing CloudFront and accepting
plain HTTP. The \name{cdn} module therefore does not write the policy: it returns the statement that
grants read access to its distribution, and the \name{storage} module merges it with its own and
attaches the result. The statement names the CloudFront service with a condition on the ARN of the
distribution, so the processed bucket accepts no other reader and a segment can be fetched only
through the signed distribution.

\subsection{Index Creation at Start-up}

The free Atlas cluster limits concurrent requests and operations per second
(Section~\ref{sec:performance-design}). Creating indexes is idempotent and cheap for one instance, so
it first ran before each instance served its first request. Under a burst of uploads, however, the
reserved concurrency of the API let dozens of instances start together, each sending its index
commands to the cluster at the same moment; the cluster refused them as too many concurrent requests,
start-up passed its timeout and the uploads that reached those instances received 502.
Indexes change only when the API code changes, so they are now created by a maintenance action that
deployment invokes directly. The action cannot be reached through the Function URL: the API accepts it
only from a direct invocation, which needs an IAM permission that only the operator holds.

The tests of the access rule matter most for security. They assert that a private, unready or
scheduled video is answered with not-found rather than forbidden to anyone but its owner, because a
forbidden answer would confirm that a video with that identifier exists; that a members-only video
returns no playlist address to a non-member; and that the key endpoint refuses another origin,
another video, another upload version or a missing token, and stops serving the key once the video is
removed.

The end-to-end tests sign in through the API in a set-up step, so no password appears in a test. The
pipeline test is the longest: it uploads a 36-second clip through the interface, waits until the
video is ready, plays it through the CDN with its key, edits it in the studio and deletes it. The
other files cover the pages of a guest, a viewer, a creator and an administrator, and the embedded
player inside a page of another origin. All 27 tests pass against production; the measured behaviour of the deployed system is presented in
Chapter~\ref{chap:evaluation}.
