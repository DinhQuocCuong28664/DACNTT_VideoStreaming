\chapter{Development and Testing}
\label{chap:implementation}

This chapter describes how the design of Chapter~\ref{chap:design} was implemented: the backend,
the transcoder, the infrastructure code and the delivery pipeline. It then records the problems met
while deploying the system and how each was solved, and ends with the automated tests.

\section{Backend Implementation}
\label{sec:backend-impl}

The backend follows a layered structure: routes delegate to controllers, controllers to services,
and only services touch the data models. Keeping business logic out of route handlers lets it be
unit tested without an HTTP server.

Authorisation for video access lives in a single service function. Every path that exposes a
video, whether the detail endpoint, the like and comment endpoints or the playback-authorisation
endpoint, calls that function. Duplicating the check across endpoints is the most common way for an
access control gap to appear, because a later change updates one copy and not the others.

Operational authority follows the same principle. The four roles, user, operator, auditor and
administrator, are mapped to permissions in one table, and each route asks whether the requester
holds a named permission, such as \texttt{moderation:review} or \texttt{metrics:read}, instead of
comparing role names. The requester's role is read from the database on every request and is not
copied into the token, so demoting a person takes effect at once rather than when a token expires.

A moderation decision is applied by one service function. It checks the reason code against the
closed list for that decision, refuses to let an operator change a decision that an administrator
made, copies the machine's verdict into \texttt{autoStatus} only if no earlier decision has done so,
resolves the open reports on the video, and then appends the event. If writing the event fails, the
decision stands and the failure is logged: withdrawing a removal because of a faulty log would be
worse, and the error rates are computed from the video documents, so a missing event does not skew
them.

The server validates upload metadata before issuing a pre-signed URL, because a user can call the
API directly and would otherwise obtain a URL for any file, turning the storage bucket into free
hosting. It checks the declared MIME type against an allow-list of video formats and refuses files
above the configured ceiling; the single and multipart paths are those of
Section~\ref{sec:upload-design}. Upload also requires a verified e-mail address. The upload guard,
the profile the interface reads and the takeover of an account by a Google sign-in all read
verification through one method of the user model, which treats an account with a Google identity
as verified. The guard runs ahead of the upload rate limiter, so a refused request does not use up
the hourly quota.

Several protections were added at the HTTP layer. Helmet sets the security headers. Cross-origin
requests are limited to an explicit allow-list, which Signed Cookies also require, because the CORS
specification forbids credentials together with a wildcard origin. Authentication endpoints allow
ten attempts per fifteen minutes per address, which makes password guessing impractical without
affecting legitimate users. The process refuses to start if the token signing secret is missing,
turning a dangerous runtime failure into an obvious one.

A new password is checked in two stages, at registration, reset and change alike. The first is
local: a list of the 131 passwords tried first, including common Vietnamese ones; obvious patterns
such as \texttt{12345678} or a repeated character; a common word with a few digits added or letters
swapped for digits; and the user's own name, e-mail prefix and the name of the service. The second
asks the Pwned Passwords service whether the password appears in a known breach, by the k-anonymity
protocol \cite{cloudflarekanon}: only the first five hexadecimal characters of its SHA-1 hash leave
the server. A reply slower than two seconds, or a failed lookup, counts as no answer and lets the
password through, so
registration does not depend on an outside service. Both stages apply from eight characters, the
length the user model already requires. This follows the guidance that a verifier compare a new
secret with common, expected or compromised values instead of imposing composition rules
\cite{nist80063b}.

The per-address limit on authentication does not stop one mailbox from being flooded, since an
attacker who changes address is counted afresh. A second limit therefore counts the mails sent to one
recipient, five per hour, shared by verification and reset mail. Beyond it, registration still
creates the account but skips the mail, a request to resend the link is refused with a 429 response,
and a reset request returns the same generic reply as every other outcome, so it still does not
reveal which addresses have an account.

\section{Transcoder Implementation}
\label{sec:transcoder-impl}

The transcoder is a Node.js worker packaged with FFmpeg in a Docker image built in several stages.
Node 18 was abandoned because Mongoose 9 needs the Web Crypto API, which that version lacks, and
Node 20 was later replaced with \texttt{node:24-slim} when Node 20 reached end of life on 30 April
2026. Node 24 was preferred over Node 26 because it is the Active LTS release, supported until April
2028. The Alpine variant was avoided because FFmpeg requires glibc.

A duplicate job must not overwrite a finished result. The heartbeat of Section~\ref{sec:pipeline-design}
is in effect a lease in the sense of Burrows \cite{burrows2006chubby}, and Burrows identified its
classical failure: a lease can expire while its holder is merely stalled, so a second holder is
granted the same resource while the first is still alive. A review of the pipeline against this
failure found that neither \texttt{updateVideoReady} nor \texttt{updateVideoError} checked the
current status before writing, so a duplicate job could overwrite a successful result or even turn a
\texttt{READY} video back into \texttt{ERROR}. Both are now a conditional \texttt{findOneAndUpdate}
that writes only when the status is not already \texttt{READY}, and \texttt{processVideo} checks the
status before downloading anything, so a late duplicate stops at once.

A single FFmpeg invocation produces every rendition that the source can fill, which decodes the
source only once. The ladder has six rungs, from 144p at 120~kbit/s to 1080p at 4~Mbit/s, and each
rung fits the source inside its frame without enlarging it: a 480p source yields a 360p rung and one
at 854$\times$480, not a 1080p rendition enlarged 2.25 times. Only the single-container path for a
video longer than twenty minutes keeps the earlier ladder of 360p, 720p and 1080p, to stay within the
time limit of a job. The command writes six-second segments and the rendition playlists; the worker
then writes the master playlist. Its bandwidth values are the peak segment bit rates measured from
the segments (Section~\ref{sec:qoe-playback}), and its codec strings are read from each stream's
sequence parameter set, since the constraint-set byte that RFC~6381 requires appears in neither the
profile name nor the level reported by a probe. A thumbnail is extracted in a separate pass.

The chunked path of Section~\ref{sec:chunked-design} runs the same image under four commands. The
planner computes chunk boundaries with functions that do no input or output, so the arithmetic is
tested directly: a boundary is a whole number of groups of pictures counted in frames, and every
chunk writes its timestamps from the same base offset, so independently encoded chunks join without
a gap or a repeated segment. A chunk job reads only its own range of the source over HTTP and
encodes every rendition for it, and the finalizer joins the playlists and measures each rendition's
bandwidth from the segments. Chunk jobs use their own task size of 4~vCPU and 8~GiB, which measured
14\% faster and used 7\% fewer vCPU-seconds than one vCPU; the size is checked against the valid
Fargate combinations when the configuration loads, because Batch would otherwise reject the
submission only after the video had been marked as processing.

Content screening is one function, called by the single-container job and by the finalizer with the
same policy and thresholds. It extracts the sampled frames with FFmpeg, sends them to Rekognition
three at a time with retries and client-side rate limiting, applies the label policy of
Section~\ref{sec:screening-design}, and returns the verdict with its evidence labels and the share of
frames analysed. An error inside the step becomes a flagged verdict carrying the error, so the video
waits for a person and is neither lost nor published. Screening is on unless
\texttt{MODERATION\_ENABLED} is explicitly false, so a missing setting cannot publish every video
unchecked.

When FFmpeg fails, the top-level handler records \texttt{ERROR} in the database. In \texttt{worker}
mode it also leaves the SQS message in flight, so the message is redelivered and, after the
configured attempts, moved to the dead letter queue. The deployed system runs \texttt{batch} mode
(Section~\ref{sec:pipeline-design}), where the container holds no message, so only the
\texttt{ERROR} record applies there; retry and alerting for that path are described in
Section~\ref{sec:challenges}.

\section{Infrastructure as Code}
\label{sec:iac}

The AWS environment is described by the thirteen Terraform modules of
Table~\ref{tab:terraform-modules} and by three environment definitions: \texttt{dev}, which hosts
the deployed system; \texttt{staging}, a reduced copy used to test a branch before it is merged; and
\texttt{prod}, a variant with On-Demand Fargate capacity, thirty days of logs and buckets that cannot
be force-destroyed. Only the first two have been applied; \texttt{prod} was checked with
\texttt{terraform validate} and never deployed. Because \texttt{dev} serves real users, it carries the
same protection against a mistaken \texttt{terraform destroy}: its buckets and registry cannot be
force-deleted while they hold objects or images, and a deleted secret stays recoverable for seven days.

Two settings deserve mention. The S3 lifecycle policy moves raw source files to Glacier after thirty
days, since they are not read again once transcoding has succeeded but must be kept in case a

manifests, which change when the set of renditions changes, a short one.

The security gate has two tiers. Most high-severity findings come from transitive dependencies that
have no patch yet, so a gate that failed on every critical or high finding would fail constantly for
reasons the team cannot act on, and developers would learn to ignore it. The pipeline therefore
reports critical and high findings without blocking, and blocks a merge only on a critical finding
that has a fix. Every failure of the gate is thus something the team can act on.

Static analysis uses \texttt{eslint-plugin-security} rather than SonarQube, which avoids running a
separate analysis server. Its rules detect, for example, commands built from user input, regular
expressions open to catastrophic backtracking and unsafe random number generation. A false positive
is suppressed only with an inline comment stating why. Infrastructure code has its own workflow,
which checks formatting, initialises without a remote backend so that no credentials are needed,
validates both environments and scans the configuration for insecure settings.

A later audit of the pipeline tightened two points. All five workflows that ran the vulnerability
scanner referenced \texttt{aquasecurity/trivy-action@master}, a branch whose content can change at any
time, so a compromise of that repository would have run inside a pipeline holding AWS credentials.
The references are now pinned to a release commit, with the version kept in a comment. The audit also
found that the Lambda submitter held \texttt{batch:SubmitJob} on every resource; it is now limited
to the project's job queue and job definition. \texttt{batch:DescribeJobs} keeps its wildcard because
AWS offers no resource-level control for it, and the module says so in a comment.

\subsection{CloudFront in a Second Account}

The content protection of Section~\ref{sec:content-protection} was implemented and tested before it
could be provisioned. AWS requires a manual verification before a new account may create CloudFront
distributions, and the request to lift that restriction stayed pending with no date. Until then the
processed-content bucket was reachable directly, so the private setting had no effect at the storage
layer.

The distribution was therefore provisioned in a second AWS account. Terraform needed no duplicated
module: the distribution, its Origin Access Control, its cache and response-header policies and its
trusted key group take an explicit \texttt{provider} argument pointing at the second account, while
the buckets, Batch, Lambda and the database stay in the first. Only the bucket policy cannot move,
since only the account owning a bucket can attach its policy. This needed no special handling,
because an Origin Access Control policy names a service principal with an \texttt{AWS:SourceArn}
condition on the distribution, whichever account owns it. With the distribution in place, the
temporary public bucket policy was removed.

\subsection{Retry and Alerting on the Deployed Path}

On the deployed path the Lambda submitter deletes the SQS message once the job is submitted, so the
queue has nothing to redeliver, and the job definition originally declared no retry strategy.
Nothing retried a failed job at any layer, and a transient fault, such as a network error while
downloading the source, lost the video with nothing but an \texttt{ERROR} record. Detection was no
better: the alarm described as ``video transcoding failures detected'' watched the dead letter queue,
which receives a message only when the Lambda fails to submit, so a job failing after submission was
invisible to it.

The job definition now declares three attempts. It retries infrastructure faults, exits at once when
the exit status shows that FFmpeg rejected the content, and has a two-hour timeout that bounds a
process stalled on malformed input. Because AWS Batch publishes no CloudWatch metric for failed jobs,
an EventBridge rule matches transitions to \texttt{FAILED} and publishes to the alert topic with the
\texttt{statusReason} of the job, and the old alarm's description now states what it really covers.

The visibility suite matters most for security. It asserts that a private video is absent from the
public listing, remains accessible to its owner, and returns not-found rather than forbidden to anyone
else, since a forbidden response would confirm that a video with that identifier exists.

The suite caught two defects before they reached users. An early version of the signing service
produced a canned policy, which the tests flagged because the cookie set held an expiry field
instead of a policy field; canned policies do not allow wildcard resources, so every video would
have failed to play once deployed. The second was the unconditional write of
Section~\ref{sec:transcoder-impl}. Six tests now pin its contract: a normal write succeeds while the
video is not yet \texttt{READY}, a write that loses the race returns the winning record instead of
throwing, and a late failure can never turn a \texttt{READY} video into \texttt{ERROR}. Run against
the original implementation, four of the six failed; the two that passed were the not-found cases,
which neither version distinguishes. The tests therefore exercise the fixed code path rather than
passing by accident of their data.
